## 2. 测试范围与目标

### 2.1 测试范围

本次测试覆盖以下四个核心模块：

| 模块 | 子系统 | 测试文件 |
|---|---|---|
| 记忆系统 | memory_save / memory_search / memory_load_context / memory_update_md / audit_log | `tests/test_memory.py` |
| 模型路由器 | resolve_model / get_routing_summary / _is_confidential | `tests/test_router.py` |
| Webhook 网关 | /health / / / /webhook/gitlab / /webhook/alertmanager | `tests/test_gateway.py` |
| 安全机制 | 涉密路由隔离、HITL 拦截、签名验证、profile 隔离 | 跨模块 |

**不在本次测试范围内**：外部服务依赖（飞书、真实 GitLab、Prometheus、ELK、K8s）、GPU 推理节点、生产部署后的端到端验收。

### 2.2 测试目标

**功能测试目标**

验证记忆系统的读写、检索、上下文加载和审计日志功能符合设计规格，模型路由器在各种 Profile 和技能组合下产生正确的路由决策，Webhook 网关正确处理 GitLab 事件和 Alertmanager 告警。

**安全测试目标**

验证涉密 Profile 在任何情况下均不路由至云端节点，高危工具在无审批时被拦截，Webhook 请求未通过签名验证时返回 403，不同租户的记忆数据相互隔离。

**集成测试目标**

验证模块间协作链路的完整性：Webhook 接收事件→技能触发→路由决策→记忆读写→结果输出的端到端流程正确执行。

**性能基准测试目标**

建立关键路径的性能基线，确保 FTS5 检索延迟、路由决策延迟、上下文加载延迟满足生产可用要求。

## 3. 测试策略

### 3.1 测试类型与分层

```
┌─────────────────────────────────────────────────────┐
│               Phase 2（待实施）                      │
│    E2E 验收测试（飞书/GitLab/K8s 完整链路）          │
├─────────────────────────────────────────────────────┤
│               Phase 1（本次实施）                    │
│  集成测试（模块间交互 + Webhook 网关 HTTP 层）       │
├─────────────────────────────────────────────────────┤
│               Phase 1（本次实施）                    │
│  安全测试（涉密路由 / HITL / 签名验证）              │
├─────────────────────────────────────────────────────┤
│               Phase 1（本次实施）                    │
│  单元测试（记忆系统 / 模型路由器）                   │
└─────────────────────────────────────────────────────┘
```

### 3.2 测试方法

| 测试类型 | 方法 | 说明 |
|---|---|---|
| 单元测试 | 白盒测试，逐函数验证 | 直接调用内部函数，验证输入输出和边界条件 |
| 安全测试 | 黑盒 + 白盒结合 | 模拟恶意输入（错误 Token、越权 Profile），验证拦截机制 |
| 集成测试 | 灰盒测试，HTTP 客户端模拟 | 通过 `httpx.AsyncClient` 发送真实 HTTP 请求，验证接口行为 |
| 性能测试 | 基准测量 | 记录关键操作耗时，建立 v1.0.0 性能基线 |

### 3.3 测试工具

| 工具 | 版本 | 用途 |
|---|---|---|
| Python unittest | 3.13.5 内置 | 单元测试框架 |
| SQLite | 3.46.1 | 记忆系统存储后端（FTS5 检索） |
| FastAPI TestClient / httpx | 集成测试 | Webhook 网关 HTTP 接口测试 |
| re（标准库） | 内置 | 中文分词辅助处理 |
| tempfile（标准库） | 内置 | 测试用临时数据库隔离 |

### 3.4 测试数据策略

- 单元测试使用内存或临时数据库，每个测试用例独立初始化，测试后自动清理。
- 集成测试使用固定测试 Token（`test_webhook_secret_123`），通过环境变量注入，不写入代码仓库。
- 所有测试数据不包含真实业务数据，使用语义等价的脱敏替代数据。

#### 9.1.2 FTS5 中文检索问题：发现→根因分析→修复验证

**问题发现**

在初始测试中，对中文关键词执行 FTS5 检索时出现零命中现象：

```
MATCH '多'          → 0 条
MATCH '多租户越权'  → 0 条
```

这与预期不符，因为数据库中确实存在包含"多租户越权"的记录。

**根因分析**

SQLite 3.46.1 的 FTS5 `unicode61` 分词器对连续汉字序列的处理策略是**将整段汉字序列作为一个整体 token 存储**，而非按单字或词组分词。

以"多租户越权修复经验"为例：
- 分词器存储的 token 是 `多租户越权修复经验`（整串）
- 查询 `MATCH '多'` 无法匹配，因为 token 不等于单字
- 查询 `MATCH '多租户越权'` 也无法匹配，因为 token 是更长的串

FTS5 的前缀通配符 `*` 可以匹配 token 的**前缀**：
- 查询 `MATCH '"多租户"*'` → 1 条 ✅（因为"多租户越权修复经验"以"多租户"开头）

**修复方案**

在 `memory_search` 函数中实现三层检索策略：

1. 提取中文片段：使用 `re.findall(r'[\u4e00-\u9fff]+', query)` 识别连续汉字子串
2. 构造前缀通配查询：每个汉字子串加 `"seg"*` 前缀通配，多个子串用 OR 连接
3. 降级兜底：FTS 无结果时降级为 SQL `LIKE '%seg%'` 查询
4. ASCII 词项：直接作为 FTS 词项，不加通配

## 12. 测试结论与上线建议

### 12.1 测试结论

Qixuan Agent v1.0.0 完成了 Phase 1 全量测试，已执行的 23 个核心测试用例和 17 个补充验证场景**全部通过**，通过率 100%。

测试期间发现 1 个缺陷（BUG-001：FTS5 中文检索零命中），已在同次迭代内完成根因分析和修复，修复后验证通过。

**核心功能验证结论**：
- 记忆系统的写入、检索、上下文加载和审计日志功能行为正确，中文检索缺陷已修复。
- 模型路由器在所有 Profile / 技能 / Role 组合下产生正确路由，优先级规则（涉密 > 技能 > 默认）严格执行。
- Webhook 网关正确处理 GitLab MR、Tag Push 和 Alertmanager 三类事件，签名验证机制有效。

**安全机制验证结论**：
- 涉密 Profile 路由隔离机制可靠，无云端泄露路径。
- HITL 高危工具拦截白名单配置正确。
- Webhook 签名验证正常拦截未授权请求。

### 12.2 上线建议

**建议：可在内部环境部署，外部服务集成测试（Phase 2）完成后方可全量上线。**

具体建议如下：

1. **立即可部署**：记忆系统、模型路由器、Webhook 网关核心功能均已验证，可在受控内网环境试运行。

2. **上线前必须完成**：HITL 完整审批流 E2E（TC-INT 系列中的 P0 用例），该机制是高危操作的最后防线，必须在真实飞书环境中端到端验证后方可允许生产流量接入 K8s / 告警处置等高危技能。

3. **监控建议**：上线初期对以下指标重点监控——Webhook 403 率（签名异常告警）、memory_search 耗时（FTS5 检索性能基线对比）、涉密路由日志（实时审计 base_url 是否含云端地址）。

4. **FTS5 中文检索**：修复方案已验证可用，建议在生产数据量（预估 10,000+ 条记忆）下补充一次性能基准测试，确认 LIKE 降级路径的耗时在可接受范围内。

5. **后续迭代**：Phase 2 测试（特别是 K8s 操作和 HITL E2E）建议优先排期，这两个场景风险等级最高（High），是 v1.1.0 上线的前置条件。
