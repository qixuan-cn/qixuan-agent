## 3. 功能模块详细设计

### 3.1 三层持久化记忆系统

**源文件**：`tools/memory/memory_tools.py`

#### 3.1.1 模块概述与职责定位

记忆系统为 Agent 提供跨会话、跨项目的持久化知识存储能力，解决大语言模型上下文窗口有限、无法长期记忆的问题。系统采用三层结构：

- **第一层（FTS 检索层）**：`memory_fts` 表，基于 SQLite FTS5 引擎，支持中英文全文检索。
- **第二层（元数据索引层）**：`memory_meta` 表，存储分类标签、项目归属、时间戳等结构化索引字段。
- **第三层（上下文缓存层）**：`USER.md` / `MEMORY.md` 文件，为 Agent 提供即时可用的上下文注入内容。

#### 3.1.2 功能点清单

| 函数 | 功能描述 | 关键参数 | 返回值 |
|------|----------|----------|--------|
| `init_db(profile)` | 初始化 SQLite 数据库，创建三张核心表 | `profile: str` — 用户/项目档案标识 | 无（副作用：建表） |
| `memory_save(...)` | 写入记忆片段 | 见下表 | `{status, rowid, profile, category, title, timestamp}` |
| `memory_search(...)` | 全文检索记忆片段 | `query, profile, category, project_id, limit` | 命中记忆列表 |
| `memory_load_context(profile)` | 加载上下文 Markdown 文件 | `profile: str` | `{user_md, memory_md, total_chars, profile}` |
| `memory_update_md(...)` | 更新 MEMORY.md / USER.md 中的 Section | `section, content, profile, file` | `{status: appended\|updated, file, profile}` |
| `audit_log_write(...)` | 写审计日志条目 | `tool_name, profile, session_id, input_data, status` | `log_id: int` |
| `audit_log_update(...)` | 更新审计日志状态 | `log_id, status, approver, profile` | 无 |

**`memory_save` 参数明细**：

| 参数 | 类型 | 必选 | 说明 |
|------|------|------|------|
| `title` | str | 是 | 记忆标题，用于摘要展示 |
| `content` | str | 是 | 记忆正文内容 |
| `category` | str | 是 | 记忆分类，见下方四类说明 |
| `tags` | list[str] | 否 | 自由标签列表 |
| `profile` | str | 是 | 档案标识，隔离不同用户/项目 |
| `session_id` | str | 否 | 来源会话 ID，便于溯源 |
| `project_id` | str | 否 | 项目 ID，支持跨项目检索过滤 |
| `source` | str | 否 | 记忆来源标注（如 `auto`, `manual`） |
| `token_count` | int | 否 | 内容 Token 数，用于容量管控 |

**记忆四分类说明**：

| 分类标识 | 业务含义 | 典型内容示例 |
|----------|----------|--------------|
| `skill_experience` | 技能经验 | "调用 Prometheus API 时需要加 Bearer Token" |
| `project_decision` | 项目决策 | "客户 A 要求所有 MR 必须 2 人 Review" |
| `bug_resolution` | 缺陷解决 | "OOMKilled 问题通过限制 JVM 堆内存解决" |
| `customer_note` | 客户备注 | "客户 B 联系人为张三，沟通风格偏好简洁" |

#### 3.1.3 核心处理流程

**全文检索流程（memory_search）**：

```
输入：query, profile, category, project_id, limit
  │
  ├─ 判断 query 字符集
  │    ├─ 含中文字符 ──▶ 分词为前缀通配 OR 表达式
  │    │                 例："代码审查" → "代"* OR "码"* OR "审"* OR "查"*
  │    └─ 纯 ASCII   ──▶ 使用原词精确匹配
  │
  ├─ 执行 FTS5 SELECT（含 category / project_id 过滤）
  │
  ├─ 若 FTS5 返回 0 条结果
  │    └─ 兜底执行 LIKE '%query%' 模糊查询
  │
  └─ 返回命中列表（按相关性排序，受 limit 控制）
```

**上下文加载流程（memory_load_context）**：

```
读取 {profile}/USER.md   ──▶ 截断至 ≤3000 字符
读取 {profile}/MEMORY.md ──▶ 截断至 ≤5000 字符
合并 total_chars 统计
返回 {user_md, memory_md, total_chars, profile}
```

**数据库结构**：

```sql
-- FTS5 全文检索表
CREATE VIRTUAL TABLE memory_fts USING fts5(
    title, content, category, tags,
    tokenize="unicode61"
);

-- 结构化元数据表
CREATE TABLE memory_meta (
    rowid       INTEGER PRIMARY KEY,
    profile     TEXT,
    session_id  TEXT,
    project_id  TEXT,
    source      TEXT,
    token_count INTEGER,
    timestamp   TEXT
);

-- 审计日志表
CREATE TABLE audit_log (
    log_id      INTEGER PRIMARY KEY AUTOINCREMENT,
    tool_name   TEXT,
    profile     TEXT,
    session_id  TEXT,
    input_data  TEXT,
    status      TEXT,
    approver    TEXT,
    created_at  TEXT,
    updated_at  TEXT
);
```

#### 3.1.4 异常处理与边界情况

| 场景 | 处理策略 |
|------|----------|
| SQLite 文件不存在 | `init_db` 自动创建数据库文件及目录 |
| USER.md / MEMORY.md 不存在 | `memory_load_context` 返回空字符串，不抛出异常 |
| 内容超出字符限制 | 硬截断至上限，不报错，截断信息记录于日志 |
| FTS5 查询语法异常 | 捕获异常后降级为 LIKE 兜底查询 |
| 写入失败 | 抛出异常，调用方负责重试或告警 |

#### 3.1.5 安全约束与合规说明

- 每个 `profile` 拥有独立数据隔离空间，查询时必须携带 `profile` 参数，禁止跨 profile 查询。
- `audit_log` 表不可删除，仅允许状态更新，保证操作可审计性。
- `input_data` 字段存储时应对敏感信息（如密钥、密码）进行脱敏处理，由上层调用方负责。

### 3.2 安全模型路由器

**源文件**：`governance/router.py`

#### 3.2.1 模块概述与职责定位

模型路由器是 Agent 的"大脑选择器"，根据当前用户档案的涉密级别、激活的技能类型以及调用方的显式指定，动态决定使用哪个大语言模型处理当前任务。设计目标是在性能、成本与安全合规之间取得最优平衡。

**四个模型角色定义**：

| 角色标识 | 模型 | 定位 |
|----------|------|------|
| `primary` | GLM-5.1 | 默认通用模型，适合综合推理与对话 |
| `coding` | Qwen3-235B-A22B | 代码分析、代码生成、代码审查专用 |
| `fast` | DeepSeek-V4-Flash（cheapest） | 低延迟、低成本，适合简单分类与快速响应 |
| `confidential_local` | gemma-4-26b-a4b-it（内网 vLLM） | 涉密数据专用，完全离线，不经公网 |

#### 3.2.2 功能点清单

| 函数 | 功能描述 | 参数 | 返回值 |
|------|----------|------|--------|
| `resolve_model(profile, active_skill, override_role)` | 执行三级路由决策，返回模型配置 | `profile: str`，`active_skill: str`，`override_role: str \| None` | 模型配置字典（含注入后的 `api_key`） |
| `resolve_embedding_model()` | 返回本地嵌入模型配置 | 无 | BGE-M3 配置字典 |
| `_is_confidential(profile)` | 判断档案是否涉密 | `profile: str` | `bool` |
| `_inject_api_key(config)` | 从环境变量注入 API Key | `config: dict` | 注入后的 `config`（含警告字段） |
| `get_routing_summary(profile, active_skill)` | 生成可读路由摘要 | `profile, active_skill` | `str`（人类可读路由说明） |

**技能→模型路由覆盖映射**：

| 技能标识 | 路由目标 | 路由原因 |
|----------|----------|----------|
| `qixuan-req-analyzer` | `coding` | 需求解析需要代码级理解能力 |
| `qixuan-code-reviewer` | `coding` | 代码审查核心场景 |
| `qixuan-ops-sentinel` | `primary` | 运维巡检以推理判断为主 |
| `qixuan-release-notes` | `coding` | 生成发版记录需解析 Commit 与 Diff |

#### 3.2.3 核心处理流程

**三级路由决策流程（resolve_model）**：

```
输入：profile, active_skill, override_role
  │
  ├─ 第一级：涉密强制路由
  │    └─ _is_confidential(profile) == True
  │         └─▶ 强制返回 confidential_local 模型配置
  │              （此级优先级最高，不可被覆盖）
  │
  ├─ 第二级：显式覆盖路由
  │    └─ override_role 不为 None
  │         └─▶ 返回 override_role 对应模型配置
  │
  ├─ 第三级：技能覆盖路由
  │    └─ active_skill 存在于技能覆盖映射表
  │         └─▶ 返回映射表中对应模型配置
  │
  └─ 默认路由
       └─▶ 返回 primary（GLM-5.1）模型配置
  │
  └─ 所有路径均执行 _inject_api_key(config)
       ├─ 从对应环境变量读取 api_key
       ├─ 移除 api_key_env 字段（防止密钥标识泄露）
       └─ api_key 缺失时在返回值中附加 warning 字段
```

**涉密判断逻辑**：

```python
def _is_confidential(profile: str) -> bool:
    # profile 以 "confidential" 开头即判定为涉密档案
    return profile.startswith("confidential")
```

#### 3.2.4 异常处理与边界情况

| 场景 | 处理策略 |
|------|----------|
| `api_key` 环境变量未设置 | 返回配置字典并附加 `warning` 字段，不抛出异常，由调用方决定是否继续 |
| `override_role` 为未知角色 | 记录警告日志，降级为默认 `primary` 路由 |
| `active_skill` 未在映射表中 | 自然穿透至默认路由，无异常 |
| 内网 vLLM 服务不可达 | 由模型调用层处理连接超时，路由器不感知 |

#### 3.2.5 安全约束与合规说明

- `api_key` 仅从环境变量读取，禁止硬编码于配置文件或代码中。
- 路由决策日志中不打印 `api_key` 值，仅记录是否注入成功。
- 涉密档案的路由覆盖逻辑为硬性约束，任何 `override_role` 参数对 `confidential_*` profile 均无效。

### 3.3 HITL 人工审批治理

**源文件**：`governance/hitl.py`

#### 3.3.1 模块概述与职责定位

HITL（Human-In-The-Loop）模块为高危工具操作提供强制性人工审批拦截机制。Agent 执行可能造成不可逆影响的操作前，必须通过飞书交互卡片获得授权人明确批准，审批结果全程记录于审计日志。

**高危工具集合（需强制审批）**：

| 工具名 | 风险级别 | 操作描述 |
|--------|----------|----------|
| `git_push` | 高 | 推送代码至远端仓库 |
| `db_execute_write` | 高 | 执行数据库写操作 |
| `send_external_email` | 高 | 向外部发送邮件 |
| `deploy_staging` | 高 | 部署至预发布环境 |
| `k8s_pod_restart` | 高 | 重启 Kubernetes Pod |

#### 3.3.2 功能点清单

| 函数/类 | 类型 | 功能描述 |
|---------|------|----------|
| `HITLTimeoutError` | Exception | 审批等待超时（>600 秒）时抛出 |
| `HITLRejectedError` | Exception | 审批人点击拒绝时抛出 |
| `requires_approval(tool_name)` | 函数 | 判断工具是否需要审批 |
| `request_approval(...)` | 异步函数 | 发起审批请求并阻塞等待结果 |
| `handle_approval_callback(log_id, action, approver)` | 函数 | 处理飞书卡片回调 |
| `hitl_guard(tool_name)` | 装饰器 | 自动注入 HITL 拦截的装饰器 |

**`request_approval` 参数明细**：

| 参数 | 类型 | 说明 |
|------|------|------|
| `tool_name` | str | 高危工具名称 |
| `tool_args` | dict | 工具调用参数，展示给审批人 |
| `profile` | str | 当前用户档案 |
| `session_id` | str | 当前会话 ID |
| `requester` | str | 发起请求的 Agent/用户标识 |

**返回值**：`{approved: True, approver: str, log_id: int}`

#### 3.3.3 核心处理流程

**审批请求完整流程**：

```
调用 request_approval(tool_name, tool_args, ...)
  │
  ├─ 检查 HITL_ENABLED 环境变量
  │    └─ HITL_ENABLED=false ──▶ 直接返回（跳过审批）
  │
  ├─ 调用 audit_log_write() 创建审计记录
  │    └─ 返回 log_id
  │
  ├─ 注册至 _pending_approvals[log_id]
  │    └─ 初始状态：{status: "pending"}
  │
  ├─ 调用 im_card_sender() 发送飞书审批卡片
  │    └─ 卡片内容：工具名 + 参数摘要 + ✅确认 / ❌拒绝 按钮
  │
  └─ 轮询等待（每 5 秒检查一次，最长等待 600 秒）
       │
       ├─ _pending_approvals[log_id].status == "approved"
       │    ├─ 调用 audit_log_update(log_id, "approved", approver)
       │    └─ 返回 {approved: True, approver, log_id}
       │
       ├─ _pending_approvals[log_id].status == "rejected"
       │    ├─ 调用 audit_log_update(log_id, "rejected", approver)
       │    └─ 抛出 HITLRejectedError
       │
       └─ 超时（600 秒无响应）
            ├─ 调用 audit_log_update(log_id, "timeout", None)
            └─ 抛出 HITLTimeoutError
```

**飞书卡片回调流程（handle_approval_callback）**：

```
接收回调：{log_id, action, approver}
  │
  ├─ 检查 log_id 是否在 _pending_approvals 中
  │    └─ 不存在 ──▶ 返回错误（可能已超时或重复回调）
  │
  ├─ action == "approve"
  │    └─ 更新 _pending_approvals[log_id].status = "approved"
  │         & .approver = approver
  │
  └─ action == "reject"
       └─ 更新 _pending_approvals[log_id].status = "rejected"
            & .approver = approver
```

**装饰器用法示例**：

```python
@hitl_guard("git_push")
async def push_code(branch: str, force: bool = False):
    # 实际推送逻辑
    ...
```

#### 3.3.4 异常处理与边界情况

| 场景 | 处理策略 |
|------|----------|
| 飞书消息发送失败 | 记录错误日志，审批流程继续等待（不自动批准） |
| 审批人重复点击 | `handle_approval_callback` 检查状态，已处理的回调直接返回，不重复更新 |
| 进程重启（pending_approvals 丢失） | 已发出的审批卡片按钮回调将无法匹配，建议生产环境替换为 Redis 持久化 |
| `HITL_ENABLED=false` | 所有高危工具跳过审批，仅适用于开发/测试环境 |
| 超时后收到回调 | log_id 不在 `_pending_approvals` 中，回调被静默忽略 |

#### 3.3.5 安全约束与合规说明

- 审批结果必须写入 `audit_log`，不可绕过。
- 生产环境 `HITL_ENABLED` 必须为 `true`，禁止关闭。
- `_pending_approvals` 为进程内字典，存在单点故障风险；生产环境**必须**替换为外部存储（如 Redis）。
- 飞书卡片回调端点须验证来源（通过 Verification Token），防止伪造审批。

### 3.4 统一 Webhook 路由网关

**源文件**：`gateway/webhook_router.py`

#### 3.4.1 模块概述与职责定位

Webhook 路由网关是系统与外部事件驱动系统（GitLab、Alertmanager）的集成入口，负责接收外部推送事件、验证合法性、路由至对应的 Agent 技能，统一监听在 8090 端口。CORS 策略仅允许内网来源，拒绝外网直接访问。

#### 3.4.2 功能点清单

| 端点 | 方法 | 功能描述 |
|------|------|----------|
| `/webhook/gitlab` | POST | 接收 GitLab Webhook 事件，路由至对应技能 |
| `/webhook/alertmanager` | POST | 接收 Alertmanager 告警，触发运维巡检技能 |
| `/health` | GET | 健康检查 |
| `/` | GET | 服务信息与端点列表 |

**GitLab 事件路由规则**：

| 事件类型 | 触发条件 | 路由技能 | 返回 |
|----------|----------|----------|------|
| Merge Request Hook | action ∈ {open, reopen, update}，state=opened | `qixuan-code-reviewer` | `{status: queued, skill, mr_iid}` |
| Tag Push Hook | 任意 Tag 推送 | `qixuan-release-notes` | `{status: queued, skill, tag}` |
| 其他事件 | — | 不路由 | `{status: ignored}` |

#### 3.4.3 核心处理流程

**GitLab Webhook 处理流程**：

```
POST /webhook/gitlab
  │
  ├─ 读取 Header: X-Gitlab-Token
  ├─ secrets.compare_digest(received_token, GITLAB_WEBHOOK_SECRET)
  │    └─ 验证失败 ──▶ 返回 401 Unauthorized
  │
  ├─ 解析请求体，读取 event_type
  │
  ├─ event_type == "Merge Request Hook"
  │    ├─ 检查 action ∈ {open, reopen, update} AND state == "opened"
  │    │    ├─ 条件满足 ──▶ 入队 qixuan-code-reviewer，返回 queued
  │    │    └─ 条件不满足 ──▶ 返回 ignored
  │    └─
  │
  ├─ event_type == "Tag Push Hook"
  │    └─ 入队 qixuan-release-notes，返回 queued（含 tag 名称）
  │
  └─ 其他 event_type ──▶ 返回 {status: ignored}
```

**Alertmanager Webhook 处理流程**：

```
POST /webhook/alertmanager
  │
  ├─ 验证 HMAC-SHA256 签名（若配置了 ALERTMANAGER_SECRET，可选）
  │    └─ 验证失败 ──▶ 返回 401
  │
  ├─ 过滤告警：alerts[].status == "firing"
  │
  ├─ 取前 5 条 firing 告警（防止告警风暴触发大量任务）
  │
  └─ 入队 qixuan-ops-sentinel，返回
       {status: queued, skill: qixuan-ops-sentinel, firing_count: N}
```

#### 3.4.4 异常处理与边界情况

| 场景 | 处理策略 |
|------|----------|
| Webhook 签名验证失败 | 返回 401，记录安全告警日志 |
| 请求体解析失败（非法 JSON） | 返回 400 Bad Request |
| 告警全部为 resolved（无 firing） | 返回 `{status: ignored, firing_count: 0}` |
| 告警数量超过 5 条 | 仅取前 5 条，其余丢弃，日志中记录完整数量 |
| 下游技能队列满 | 返回 503，外部系统应配置 Webhook 重试策略 |

#### 3.4.5 安全约束与合规说明

- CORS 仅允许配置白名单内的内网来源（`ALLOWED_ORIGINS`），严禁配置为 `*`。
- GitLab Token 验证使用 `secrets.compare_digest` 防止时序攻击。
- HMAC-SHA256 对 Alertmanager 为可选配置，生产环境建议启用。
- 端口 8090 应仅对内网开放，禁止直接暴露至公网。

### 3.5 飞书接入网关

**源文件**：`gateway/feishu/feishu_gateway.py`

#### 3.5.1 模块概述与职责定位

飞书接入网关是用户与 Agent 交互的主要入口，处理飞书平台推送的事件消息，包括用户@机器人消息、URL 验证握手及 HITL 审批卡片回调。系统通过白名单机制控制可访问 Agent 的用户范围。

#### 3.5.2 功能点清单

| 函数/端点 | 类型 | 功能描述 |
|-----------|------|----------|
| `_decrypt_feishu_event(encrypted)` | 内部函数 | AES-256-CBC 解密飞书加密事件 |
| `_verify_token(token)` | 内部函数 | 验证飞书 Verification Token |
| `_get_tenant_access_token()` | 异步内部函数 | 获取飞书 Tenant Access Token |
| `send_feishu_message(...)` | 异步函数 | 发送飞书消息（普通文本或交互卡片） |
| `_process_message_event(...)` | 异步内部函数 | 处理用户消息，白名单校验 + 调用 Agent |
| `POST /gateway/feishu/event` | HTTP 端点 | 主事件处理入口 |
| `GET /health` | HTTP 端点 | 健康检查，返回飞书配置状态 |

**send_feishu_message 参数**：

| 参数 | 类型 | 说明 |
|------|------|------|
| `receive_id` | str | 接收方 ID（open_id 或 chat_id） |
| `content` | str / dict | 消息内容 |
| `receive_id_type` | str | `open_id` 或 `chat_id` |
| `msg_type` | str | `text` 或 `interactive` |

#### 3.5.3 核心处理流程

**事件主处理流程**：

```
POST /gateway/feishu/event
  │
  ├─ 解密请求体（若启用加密）
  │    └─ _decrypt_feishu_event(body.encrypted)
  │         └─ AES-256-CBC 解密，key = SHA256(EncryptKey)，IV = 前16字节
  │
  ├─ 验证 Verification Token
  │    └─ _verify_token(token)
  │         └─ hmac.compare_digest 比对，失败返回 401
  │
  ├─ 读取 header.event_type
  │
  ├─ event_type == "url_verification"
  │    └─ 返回 {challenge: body.challenge}（握手验证）
  │
  ├─ event_type == "im.message.receive_v1"
  │    ├─ 立即返回 200（防止超时重试）
  │    └─ 异步执行 _process_message_event(...)
  │
  └─ event_type == "card.action.trigger"
       └─ 解析 action_value
            └─ 调用 handle_approval_callback(log_id, action, approver)
```

**消息处理流程（_process_message_event）**：

```
_process_message_event(event, sender_open_id, chat_id, text)
  │
  ├─ 检查 sender_open_id 是否在 ALLOWED_USERS 白名单中
  │    └─ 不在白名单 ──▶ 回复"无权限"提示，终止处理
  │
  ├─ 解析 text 内容，识别意图
  │
  ├─ 调用 Agent 核心（当前为占位实现）
  │
  └─ 调用 send_feishu_message() 返回 Agent 回复
```

**AES 解密流程**：

```
密钥派生：key = SHA256(FEISHU_ENCRYPT_KEY)
初始化向量：IV = encrypted_bytes[0:16]
密文：ciphertext = encrypted_bytes[16:]
明文 = AES_CBC_Decrypt(key, IV, ciphertext)
移除 PKCS7 Padding → 返回明文 JSON 字符串
```

#### 3.5.4 异常处理与边界情况

| 场景 | 处理策略 |
|------|----------|
| 解密失败（密钥错误或数据损坏） | 返回 400，记录错误日志 |
| Token 验证失败 | 返回 401，记录安全告警 |
| 用户不在白名单 | 回复权限不足提示，不抛出异常 |
| Agent 核心处理超时 | 异步处理已分离，不影响飞书平台的 200 响应 |
| Tenant Access Token 获取失败 | 重试3次后记录错误，消息发送失败 |
| 重复事件（飞书平台重试） | 应通过 event_id 实现幂等，当前版本待完善 |

#### 3.5.5 安全约束与合规说明

- `FEISHU_ENCRYPT_KEY` 和 `FEISHU_VERIFICATION_TOKEN` 必须从环境变量加载，禁止硬编码。
- `ALLOWED_USERS` 白名单机制为强制性安全控制，非白名单用户的消息不得触发 Agent 操作。
- 事件端点对公网可访问（飞书需要回调），但所有请求必须通过 Token 验证。

### 3.6 Git/GitLab 只读工具集

**源文件**：`tools/git/git_tools.py`

#### 3.6.1 模块概述与职责定位

Git/GitLab 工具集为代码审查技能（`qixuan-code-reviewer`）和发版记录技能（`qixuan-release-notes`）提供 GitLab API 的只读访问能力。工具集遵循最小权限原则，`REVIEWER_TOKEN` 仅授予只读和评论权限，不执行任何写操作（评论除外）。

#### 3.6.2 功能点清单

| 函数 | 功能描述 | 关键参数 | 返回值 |
|------|----------|----------|--------|
| `git_diff_reader(project_id, mr_iid, max_lines_per_file)` | 获取 MR 信息与变更文件 Diff | `project_id: str/int`，`mr_iid: int`，`max_lines_per_file: int = 500` | 结构化字典（含 MR 信息 + 文件 Diff 列表） |
| `git_log_collector(project_id, from_ref, to_ref, max_commits)` | 获取两 Git 引用间的提交日志 | `project_id`，`from_ref: str`，`to_ref: str`，`max_commits: int = 200` | 提交日志列表 |
| `gitlab_comment_poster(project_id, mr_iid, body, note_type)` | 发布 MR 评论 | `body: str`（≤50KB），`note_type: str` | 评论对象字典 |
| `verify_gitlab_webhook(payload_bytes, signature_header)` | 验证 Webhook 签名 | `payload_bytes: bytes`，`signature_header: str` | `bool` |

**git_diff_reader 返回结构示例**：

```json
{
  "mr_info": {
    "iid": 42,
    "title": "feat: 新增记忆检索接口",
    "author": "zhang_san",
    "source_branch": "feat/memory-search",
    "target_branch": "main",
    "state": "opened"
  },
  "files": [
    {
      "file_path": "tools/memory/memory_tools.py",
      "diff": "--- a/...\n+++ b/...\n...",
      "truncated": false
    }
  ]
}
```

#### 3.6.3 核心处理流程

**MR Diff 读取流程**：

```
git_diff_reader(project_id, mr_iid, max_lines_per_file)
  │
  ├─ 调用 GitLab API: GET /projects/{id}/merge_requests/{iid}
  │    └─ 获取 MR 基本信息
  │
  ├─ 调用 GitLab API: GET /projects/{id}/merge_requests/{iid}/diffs
  │    └─ 获取所有变更文件列表
  │
  ├─ 对每个文件：
  │    ├─ 读取 diff 内容
  │    └─ 若行数 > max_lines_per_file
  │         └─ 截断至 max_lines_per_file 行，标记 truncated=true
  │
  └─ 返回结构化字典
```

**评论发布安全检查**：

```
gitlab_comment_poster(project_id, mr_iid, body, note_type)
  │
  ├─ len(body.encode('utf-8')) > 50 * 1024
  │    └─ 截断至 50KB，附加截断提示
  │
  └─ 调用 GitLab API: POST /projects/{id}/merge_requests/{iid}/notes
```

#### 3.6.4 异常处理与边界情况

| 场景 | 处理策略 |
|------|----------|
| MR 不存在（404） | 抛出异常，返回错误信息给 Agent |
| Diff 文件数量过多 | 按文件数量上限截断，优先包含核心代码文件 |
| GitLab API 限流（429） | 指数退避重试，最多3次 |
| 单文件 Diff 超长 | 截断至 `max_lines_per_file`，标记 `truncated=true` |
| 令牌权限不足（403） | 抛出权限异常，记录审计日志 |

#### 3.6.5 安全约束与合规说明

- `REVIEWER_TOKEN` 仅用于读取 Diff 和发布评论，严禁用于合并、关闭、推送等写操作。
- 令牌值禁止出现在任何日志输出中（通过日志过滤器屏蔽）。
- 评论长度限制（≤50KB）防止意外发送超大内容导致 GitLab API 拒绝。

### 3.7 运维观测工具集

**源文件**：`tools/ops/ops_tools.py`

#### 3.7.1 模块概述与职责定位

运维观测工具集为 `qixuan-ops-sentinel` 技能提供多数据源的只读观测能力，覆盖指标（Prometheus）、日志（Elasticsearch）、容器编排（Kubernetes）三个维度。所有工具严格遵循只读原则，自动对敏感信息进行脱敏处理。

#### 3.7.2 功能点清单

| 函数 | 功能描述 | 关键参数 | 返回值 |
|------|----------|----------|--------|
| `prometheus_readonly_query(promql, time_range_hours, step)` | 执行 Prometheus range 查询 | `promql: str`，`time_range_hours: float`，`step: str` | 时序数据列表 |
| `prometheus_golden_signals(cluster_label)` | 批量查询四大黄金信号 | `cluster_label: str` | 各信号最新数据点字典 |
| `elk_log_search(keywords, service_name, log_level, minutes_back, max_hits)` | Elasticsearch 多条件日志查询 | 见下表 | 脱敏后的日志列表 |
| `k8s_readonly_inspect(namespace, resource_type, label_selector)` | kubectl 只读巡检 | `namespace: str`，`resource_type: str`，`label_selector: str` | 资源信息 + 异常 Pod 识别结果 |

**黄金信号指标定义**：

| 信号名 | PromQL 查询目标 | 单位 |
|--------|----------------|------|
| `error_rate_5xx` | 5xx 错误率 | % |
| `p99_latency_ms` | P99 请求延迟 | ms |
| `cpu_usage_max` | CPU 使用率峰值 | % |
| `memory_usage_max` | 内存使用率峰值 | % |
| `disk_usage_max` | 磁盘使用率峰值 | % |

**elk_log_search 参数明细**：

| 参数 | 类型 | 说明 |
|------|------|------|
| `keywords` | list[str] | 关键词列表，AND 逻辑组合 |
| `service_name` | str | 服务名过滤（可选） |
| `log_level` | str | 日志级别过滤（ERROR/WARN/INFO） |
| `minutes_back` | int | 查询最近 N 分钟内的日志 |
| `max_hits` | int | 最大返回条数 |

**k8s 允许查询的资源类型白名单**：
`pods` / `deployments` / `services` / `events` / `nodes` / `configmaps`

#### 3.7.3 核心处理流程

**K8s 巡检流程**：

```
k8s_readonly_inspect(namespace, resource_type, label_selector)
  │
  ├─ 验证 resource_type 在白名单中
  │    └─ 不在白名单 ──▶ 抛出 ValueError，拒绝执行
  │
  ├─ 构造 kubectl 命令：
  │    kubectl get {resource_type} -n {namespace} -l {label_selector} -o json
  │
  ├─ subprocess 执行，timeout=15 秒
  │    └─ 超时 ──▶ 抛出 TimeoutError，附带已获取的部分输出
  │
  ├─ 解析 JSON 输出
  │
  └─ 自动识别异常 Pod：
       ├─ 检测 CrashLoopBackOff 状态
       └─ 检测 OOMKilled 状态
       └─ 返回资源信息 + {anomalies: [...]}
```

**日志脱敏流程**：

```
elk_log_search 返回结果后：
  │
  └─ 对每条日志：
       ├─ 应用 _SENSITIVE_PATTERNS 正则扫描
       │    ├─ password=xxx ──▶ password=***
       │    ├─ token=xxx ──▶ token=***
       │    └─ api_key=xxx ──▶ api_key=***
       │
       └─ 单条日志截断至 ≤1000 字符
```

#### 3.7.4 异常处理与边界情况

| 场景 | 处理策略 |
|------|----------|
| Prometheus 不可达 | 返回空数据，附带错误信息字段 |
| PromQL 语法错误 | Prometheus 返回 400，转换为可读错误返回给 Agent |
| ES 查询超时 | 返回已获取的部分结果，附带超时标记 |
| kubectl 命令超时（>15s） | 强制终止进程，返回错误提示 |
| k8s 权限不足（Forbidden） | 返回权限错误，记录审计日志 |
| 资源类型不在白名单 | 拒绝执行，抛出 ValueError |

#### 3.7.5 安全约束与合规说明

- k8s 工具仅执行 `kubectl get`，严禁 `delete`、`patch`、`apply`、`exec` 等变更操作。
- 日志中的敏感字段通过 `_SENSITIVE_PATTERNS` 正则自动脱敏，模式覆盖 `password`、`token`、`api_key` 等常见字段名。
- Prometheus 和 ES 的访问凭证从环境变量读取，不硬编码。

### 3.8 IM 推送工具

**源文件**：`tools/notifications/im_notifier.py`

#### 3.8.1 模块概述与职责定位

IM 推送工具为系统提供结构化消息推送能力，支持飞书富文本卡片和钉钉 Markdown 两种消息格式。工具集成 HITL 审批按钮，支持在推送消息中直接嵌入审批交互。通过 Webhook URL 白名单防止 SSRF 攻击。

#### 3.8.2 功能点清单

| 函数 | 功能描述 | 关键参数 | 返回值 |
|------|----------|----------|--------|
| `im_card_sender(channel, title, content, status, hitl_action)` | 发送飞书富文本卡片 | 见下表 | 发送结果字典 |
| `dingtalk_notify(channel, title, content, at_all)` | 发送钉钉 Markdown 消息 | `channel: str`，`title: str`，`content: str`，`at_all: bool` | 发送结果字典 |

**im_card_sender 参数明细**：

| 参数 | 类型 | 说明 |
|------|------|------|
| `channel` | str | 飞书 Webhook URL（需在白名单中） |
| `title` | str | 卡片标题 |
| `content` | str | 卡片正文内容（支持 Markdown） |
| `status` | str | 状态级别，影响卡片颜色主题 |
| `hitl_action` | dict \| None | HITL 审批按钮配置，包含 `log_id` 和按钮文案 |

**状态→颜色映射**：

| status 值 | 颜色主题 | 使用场景 |
|-----------|----------|----------|
| `info` | 蓝色（blue） | 普通通知、巡检结果 |
| `warning` | 黄色（yellow） | 告警提示、需关注事项 |
| `critical` | 红色（red） | 紧急告警、故障通知 |
| `success` | 绿色（green） | 任务成功、部署完成 |

#### 3.8.3 核心处理流程

**飞书卡片发送流程**：

```
im_card_sender(channel, title, content, status, hitl_action)
  │
  ├─ 验证 channel URL 在 ALLOWED_WEBHOOK_URLS 白名单中
  │    └─ 不在白名单 ──▶ 抛出 SecurityError，拒绝发送
  │
  ├─ 构造飞书卡片 JSON：
  │    ├─ header: {title, color: status_color_map[status]}
  │    ├─ body: Markdown 内容块
  │    └─ actions（如果 hitl_action 不为 None）：
  │         ├─ ✅ 确认 按钮（value: {log_id, action: "approve"}）
  │         └─ ❌ 拒绝 按钮（value: {log_id, action: "reject"}）
  │
  └─ POST 卡片 JSON 至 channel URL
```

#### 3.8.4 异常处理与边界情况

| 场景 | 处理策略 |
|------|----------|
| Webhook URL 不在白名单 | 抛出安全异常，不发送，记录告警日志 |
| Webhook 请求超时 | 重试2次，仍失败则返回错误结果 |
| 飞书卡片内容过长 | 自动截断 content 字段，不抛出异常 |
| 钉钉 at_all=True 频率过高 | 由调用方控制频率，工具层不限制 |

#### 3.8.5 安全约束与合规说明

- `ALLOWED_WEBHOOK_URLS` 白名单为强制性安全控制，工具**不支持**向任意 URL 发送消息，从根本上防止 SSRF 攻击。
- Webhook URL 本身视为敏感配置，从环境变量加载，不写入代码。
- HITL 审批按钮的 `log_id` 必须来自 `audit_log`，防止伪造审批请求。

### 3.9 /learn 技能自进化

**源文件**：`scripts/learn.py`

#### 3.9.1 模块概述与职责定位

`/learn` 是 Agent 技能自我进化机制的核心脚本，通过分析历史会话轨迹，自动生成或更新标准化的 `SKILL.md` 技能描述文件，并可选择性地推送至内部技能仓库，实现 Agent 能力的持续迭代。

#### 3.9.2 功能点清单

**工作流步骤**：

| 步骤 | 操作 | 说明 |
|------|------|------|
| 1 | 加载会话轨迹 | 从 SQLite 读取指定 `session_id` 的 `tool_calls`、`decisions`、`errors` |
| 2 | 生成 SKILL.md 草稿 | 调用 LLM 生成包含 YAML frontmatter + 工具链 + 避坑要点的标准文档 |
| 3 | 保存技能文件 | 写入 `skills/qixuan/<skill-name>/SKILL.md`，自动备份旧版为 `.bak_时间戳` |
| 4 | Git 推送（可选） | `--push-to-git` 参数开启时：`git add` + `git commit` + `git push` |

**CLI 参数**：

| 参数 | 类型 | 必选 | 说明 |
|------|------|------|------|
| `--skill-name` | str | 是 | 目标技能名称（如 `qixuan-code-reviewer`） |
| `--session-id` | str | 是 | 来源会话 ID，用于查询轨迹 |
| `--profile` | str | 是 | 用户档案标识 |
| `--skills-dir` | str | 否 | 技能目录路径，默认 `skills/qixuan/` |
| `--push-to-git` | flag | 否 | 开启后自动推送至内部 Git 仓库 |

**生成的 SKILL.md 结构**：

```markdown
---
# YAML Frontmatter
skill_name: qixuan-xxx
version: x.y.z
description: 技能功能描述
tools_required:
  - tool_name_1
  - tool_name_2
---

## 工具链
...

## 避坑要点
...

## 示例会话
...
```

#### 3.9.3 核心处理流程

```
python scripts/learn.py --skill-name qixuan-code-reviewer \
                        --session-id sess_20250714_001 \
                        --profile default \
                        --push-to-git
  │
  ├─ 连接 SQLite，查询 session_id 对应的会话记录
  │    ├─ tool_calls: [工具调用序列]
  │    ├─ decisions: [LLM 决策节点]
  │    └─ errors: [发生的错误及处理]
  │
  ├─ 构造 Prompt，调用 LLM 生成 SKILL.md 草稿
  │
  ├─ 确定输出路径：{skills_dir}/{skill_name}/SKILL.md
  │
  ├─ 若文件已存在：
  │    └─ 备份为 SKILL.md.bak_{timestamp}
  │
  ├─ 写入新 SKILL.md
  │
  └─ 若 --push-to-git：
       ├─ git add {skill_file_path}
       ├─ git commit -m "learn: update {skill_name} from session {session_id}"
       └─ git push origin {branch}
```

#### 3.9.4 异常处理与边界情况

| 场景 | 处理策略 |
|------|----------|
| session_id 不存在 | 打印错误退出，不生成文件 |
| LLM 生成超时 | 重试一次，仍失败则退出并保留旧版技能文件 |
| 技能目录不存在 | 自动创建目录 |
| Git push 失败 | 文件已保存，仅打印 Git 错误，不回滚文件写入 |
| 旧文件备份失败 | 中止执行，不覆盖原文件（保护现有技能） |

#### 3.9.5 安全约束与合规说明

- `--push-to-git` 操作为高危操作，建议在 CI/CD 流水线中使用专用只写令牌。
- 生成内容经过 LLM，输出内容需经人工 Review 后再实际投入生产使用。
- 旧版本强制备份，确保技能退化时可快速回滚。

### 3.10 定时任务调度器

**源文件**：`scripts/cron_runner.py`

#### 3.10.1 模块概述与职责定位

定时任务调度器为 Agent 技能提供基于 Cron 表达式的周期性触发能力，无需依赖外部调度系统（如 Celery、Airflow），通过主循环 + croniter 实现轻量级定时调度。

#### 3.10.2 功能点清单

**工作流说明**：

| 步骤 | 操作 |
|------|------|
| 1 | 读取 `config.yaml` 中 `cron.jobs` 配置列表 |
| 2 | 主循环每 60 秒检查一次所有任务 |
| 3 | 使用 `croniter` 计算每个任务的上次触发时间 |
| 4 | 若当前时间与上次触发时间的差值 < 60 秒，触发任务执行 |

**当前配置任务**：

| 任务名 | Cron 表达式 | 触发技能 | 执行 Prompt |
|--------|-------------|----------|-------------|
| `daily_ops_inspection` | `0 8 * * 1-5` | `qixuan-ops-sentinel` | 执行工作日早间客户环境健康巡检 |

#### 3.10.3 核心处理流程

```
启动 cron_runner.py
  │
  ├─ 读取 config.yaml → cron.jobs 列表
  │
  └─ 主循环（每 60 秒）：
       │
       └─ 对每个 job：
            ├─ 解析 job.schedule（Cron 表达式）
            ├─ croniter 计算 prev_trigger_time
            ├─ delta = now - prev_trigger_time
            ├─ delta < 60s
            │    └─ 触发 Agent 技能：
            │         skill = job.skill
            │         prompt = job.prompt
            └─ delta >= 60s ──▶ 跳过
```

**Cron 表达式说明（`0 8 * * 1-5`）**：

| 字段 | 值 | 含义 |
|------|----|------|
| 分钟 | 0 | 整点 |
| 小时 | 8 | 上午 8 点 |
| 日 | * | 每天 |
| 月 | * | 每月 |
| 星期 | 1-5 | 周一至周五 |

#### 3.10.4 异常处理与边界情况

| 场景 | 处理策略 |
|------|----------|
| config.yaml 解析失败 | 程序启动时报错退出 |
| Cron 表达式非法 | croniter 抛出异常，跳过该任务，记录错误日志 |
| Agent 技能执行失败 | 记录错误日志，不影响其他任务的调度 |
| 程序重启（跨过触发时间） | 下次循环会检测到 delta < 60s，会在重启后第一个完整分钟执行补偿 |
| 多实例部署 | 当前版本不支持分布式锁，多实例部署会重复触发，建议单实例运行 |

#### 3.10.5 安全约束与合规说明

- 定时任务触发的 Agent 操作同样受 HITL 机制约束，高危操作仍需人工审批。
- 定时任务的 Prompt 内容来自 `config.yaml`，修改需走代码审查流程，防止注入恶意指令。
- 建议生产环境使用进程守护（如 `systemd`）确保调度器稳定运行。
