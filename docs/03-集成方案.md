| 6 | 内网 vLLM 推理节点 | 单向（API 调用） | HTTP（内网） | Bearer Token | ★★★★★ | 路由层（涉密 Profile） |

## 2. 集成一：飞书（Lark）机器人

### 2.1 集成概述与目的

Qixuan Agent 通过飞书企业自建应用与员工交互。员工在飞书中 @机器人 发起请求，Agent 解析消息、执行任务后以文本或富文本卡片形式回复。涉及写操作（如重启 Pod）时，Agent 推送审批卡片，通过 HITL（Human-in-the-Loop）流程由负责人在飞书内一键审批或拒绝。

### 2.2 飞书开放平台配置步骤

**前提**：具备飞书企业管理员或应用管理员权限。

1. 登录[飞书开放平台](https://open.feishu.cn)，进入「开发者后台」→「创建企业自建应用」，记录 **App ID** 和 **App Secret**。

2. 进入应用详情页 → 「功能」→「机器人」，开启机器人能力并保存。

3. 进入「权限管理」，申请以下权限（生产环境需通过审核）：

   | 权限标识 | 说明 |
   |---------|------|
   | `im:message` | 读取消息 |
   | `im:message:send_as_bot` | 以机器人身份发送消息 |

4. 进入「事件订阅」，配置请求地址：

   ```
   https://<your-domain>:8090/gateway/feishu/event
   ```

   勾选以下事件：

   | 事件标识 | 触发场景 |
   |---------|---------|
   | `im.message.receive_v1` | 用户 @机器人 发送消息 |
   | `card.action.trigger` | 用户点击交互卡片按钮 |

5. 在「事件订阅」页面开启**加密推送**，填写 `FEISHU_ENCRYPT_KEY`；填写 `FEISHU_VERIFICATION_TOKEN` 完成请求验证。

6. 点击「验证」，确认服务端正确响应 URL 验证握手（见 2.4 节），保存配置。

7. 将应用发布至企业，或通过「版本管理」审批后上线。

### 2.3 本系统侧环境变量配置

在 `.env` 文件中配置以下变量：

| 变量名 | 必选 | 说明 |
|-------|------|------|
| `FEISHU_APP_ID` | ✅ | 飞书应用 App ID，格式 `cli_xxxxxxxxxxxxxxxx` |
| `FEISHU_APP_SECRET` | ✅ | 飞书应用 App Secret |
| `FEISHU_VERIFICATION_TOKEN` | ✅ | 事件订阅页面的 Verification Token，用于验证请求合法性 |
| `FEISHU_ENCRYPT_KEY` | ✅ | 加密推送密钥，用于 AES-256-CBC 解密事件体 |
| `FEISHU_ALLOWED_USERS` | ⬜ | 允许使用机器人的用户 open_id 白名单，逗号分隔（如 `ou_xxx,ou_yyy`）；留空则允许全体员工 |

### 2.4 集成接口说明

#### 事件接收端点

| 属性 | 值 |
|-----|---|
| 地址 | `POST https://<your-domain>:8090/gateway/feishu/event` |
| 认证 | 飞书平台发起请求，本端通过 Verification Token 和 AES 解密验证合法性 |
| Content-Type | `application/json` |

**URL 验证握手**（服务首次配置时触发）：

```
请求体：
{
  "type": "url_verification",
  "challenge": "ajls384kdjx98XX",
  "token": "<FEISHU_VERIFICATION_TOKEN>"
}

响应体（200 OK）：
{
  "challenge": "ajls384kdjx98XX"
}
```

**加密事件解密流程**：

```
1. 取请求体中 encrypt 字段（Base64 字符串）
2. Base64 解码得到密文字节
3. 密文前 16 字节为 IV（AES-256-CBC）
4. 密钥 = SHA256(FEISHU_ENCRYPT_KEY) → 32 字节
5. 解密 → PKCS7 去填充 → UTF-8 解码 → JSON 解析
```

**HITL 卡片审批回调**：

```
事件类型：card.action.trigger
value 字段示例：
{
  "action_id": "hitl_approve_k8s_pod_restart",
  "log_id": "task_20250714_001"
}

处理逻辑：
  - action_id 以 hitl_approve_ 开头 → 审批通过
  - action_id 以 hitl_reject_ 开头  → 审批拒绝
  - 调用：handle_approval_callback(log_id, "approve"/"reject", operator_open_id)
```

### 2.5 安全机制

| 机制 | 实现方式 |
|-----|---------|
| 请求来源验证 | 验证事件体中 `token` 字段与 `FEISHU_VERIFICATION_TOKEN` 一致 |
| 传输加密 | AES-256-CBC，密钥由 SHA256(FEISHU_ENCRYPT_KEY) 派生 |
| 用户访问控制 | `FEISHU_ALLOWED_USERS` 白名单过滤，非白名单用户请求直接丢弃 |
| 操作审批 | 写操作（如 Pod 重启）强制经过 HITL 卡片审批，审批结果记录操作日志 |
| Secret 管理 | 所有密钥仅存于 `.env`，不入代码仓库 |

### 2.6 常见故障与排查步骤

| 故障现象 | 可能原因 | 排查步骤 |
|---------|---------|---------|
| 飞书平台提示「验证失败」 | Verification Token 不匹配 / 服务未响应 | 检查 `FEISHU_VERIFICATION_TOKEN` 配置；确认 8090 端口可公网访问；查看服务日志 |
| 收到事件但解析报错 | Encrypt Key 错误或 AES 解密失败 | 核对 `FEISHU_ENCRYPT_KEY` 与开放平台配置一致；确认密钥未包含多余空格 |
| 机器人不响应特定用户消息 | 用户不在白名单 | 检查 `FEISHU_ALLOWED_USERS` 是否包含该用户 open_id，或留空以允许所有人 |
| 卡片审批按钮点击无反应 | card.action.trigger 事件未订阅 | 确认事件订阅页已勾选 `card.action.trigger` 并重新发布应用 |
| 机器人无法发送消息 | 缺少 `im:message:send_as_bot` 权限 | 进入权限管理确认权限已申请且通过审核 |

## 3. 集成二：GitLab Webhook

### 3.1 集成概述与目的

Qixuan Agent 监听内部 GitLab 实例的 Webhook 事件：当有新的 Merge Request 创建或更新时，自动触发代码审查技能（`qixuan-code-reviewer`）并将审查意见以评论形式发布回 MR；当有新 Tag 推送时，自动生成 Release Notes。

### 3.2 GitLab 项目配置步骤

1. 进入目标 GitLab 项目 → **Settings → Webhooks**。

2. 填写 URL：

   ```
   https://<your-domain>:8090/webhook/gitlab
   ```

3. **Secret Token** 字段填写 `GIT_WEBHOOK_SECRET` 的值。

4. 勾选触发事件：

   | 事件 | 用途 |
   |-----|------|
   | Merge Request Events | 触发代码审查 |
   | Tag Push Events | 触发 Release Notes 生成 |

5. 点击「Add webhook」保存，再点击「Test」验证连通性（服务应返回 200）。

6. 在 GitLab **User Settings → Access Tokens** 中创建两个 Token：

   | 用途 | 变量名 | 所需权限 |
   |-----|-------|---------|
   | MR 信息读取 + 评论发布 | `GIT_REVIEWER_TOKEN` | `read_repository`、`write_repository`（评论）|
   | 技能仓库同步 | `GIT_SKILL_TOKEN` | `read_repository`、`write_repository` |

### 3.3 本系统侧环境变量配置

| 变量名 | 必选 | 说明 |
|-------|------|------|
| `GIT_INTERNAL_URL` | ✅ | GitLab 内部域名，如 `https://git.qixuan-soft.internal` |
| `GIT_REVIEWER_TOKEN` | ✅ | 读取 MR 信息、发布评论的 Personal Access Token |
| `GIT_WEBHOOK_SECRET` | ✅ | Webhook Secret Token，用于签名验证 |
| `GIT_SKILL_TOKEN` | ✅ | 技能仓库同步令牌 |

### 3.4 集成接口说明

#### Webhook 接收端点

| 属性 | 值 |
|-----|---|
| 地址 | `POST https://<your-domain>:8090/webhook/gitlab` |
| 认证 | 请求头 `X-Gitlab-Token` 携带 Secret Token |

**签名验证逻辑**：

```python
import secrets
header_token = request.headers.get("X-Gitlab-Token", "")
if not secrets.compare_digest(header_token, GIT_WEBHOOK_SECRET):
    return 401
```

**事件路由规则**：

| 事件类型（object_kind） | 触发条件 | 触发动作 |
|----------------------|---------|---------|
| `merge_request` | action ∈ {open, reopen, update} 且 state = opened | 触发 `qixuan-code-reviewer` |
| `tag_push` | ref 匹配 `refs/tags/*` | 触发 `qixuan-release-notes` |

#### GitLab REST API 调用

Base URL：`{GIT_INTERNAL_URL}/api/v4`
认证头：`PRIVATE-TOKEN: {GIT_REVIEWER_TOKEN}`
超时：connect=5s, read=30s, write=10s

| 方法 | 路径 | 用途 |
|-----|------|------|
| GET | `/projects/{id}/merge_requests/{mr_iid}` | 获取 MR 基本信息 |
| GET | `/projects/{id}/merge_requests/{mr_iid}/diffs?per_page=100` | 获取代码 Diff |
| POST | `/projects/{id}/merge_requests/{mr_iid}/notes` | 发布审查评论 |
| GET | `/projects/{id}/repository/commits?ref_name={ref}&per_page=100` | 获取提交日志 |

### 3.5 安全机制

| 机制 | 实现方式 |
|-----|---------|
| Webhook 签名验证 | `secrets.compare_digest` 时序安全比对，防止时序攻击 |
| Token 最小权限 | `GIT_REVIEWER_TOKEN` 仅授予必要权限，不授予 `api` 全量权限 |
| 传输加密 | 所有 GitLab API 调用走 HTTPS |
| Secret 管理 | Token 存于 `.env`，不入仓库；`.gitignore` 中排除 `.env` |

### 3.6 常见故障与排查步骤

| 故障现象 | 可能原因 | 排查步骤 |
|---------|---------|---------|
| GitLab Webhook 测试返回 401 | Secret Token 不匹配 | 核对 `GIT_WEBHOOK_SECRET` 与 GitLab 项目 Webhook 配置中的值 |
| Webhook 测试返回 200 但无动作 | 事件类型不匹配 | 检查推送的事件体中 `object_kind` 和 `action` 是否符合路由规则 |
| 评论发布失败（403） | Token 权限不足 | 确认 `GIT_REVIEWER_TOKEN` 包含评论写权限 |
| API 请求超时 | 内网 DNS 解析问题或 GitLab 负载高 | 检查 `GIT_INTERNAL_URL` 域名解析；适当放宽 read 超时 |
| 技能仓库同步失败 | `GIT_SKILL_TOKEN` 过期或权限不足 | 重新生成 Token 并更新 `.env` |

## 4. 集成三：Prometheus + Alertmanager

### 4.1 集成概述与目的

Qixuan Agent 通过两种方式与 Prometheus 交互：**主动查询**（Agent 执行 PromQL 以获取系统指标）和**被动接收**（Alertmanager 推送告警 Webhook）。Agent 可分析四大黄金信号（错误率、延迟、流量、饱和度），并在告警触发时自动启动运维排查流程。

### 4.2 外部系统侧配置步骤

**Alertmanager 配置**（`alertmanager.yml`）：

```yaml
route:
  receiver: qixuan-agent
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h

receivers:
  - name: qixuan-agent
    webhook_configs:
      - url: 'https://<your-domain>:8090/webhook/alertmanager'
        send_resolved: false
        # 若需签名验证，在 HTTP Headers 中添加：
        # http_config:
        #   authorization:
        #     credentials: '<HMAC-SHA256 签名>'
```

修改后执行：

```bash
curl -X POST http://alertmanager.qixuan-soft.internal:9093/-/reload
```

**Prometheus 配置**：Qixuan Agent 仅需只读查询权限，确认 `PROMETHEUS_READONLY_TOKEN` 对应的账户有 `/api/v1/query_range` 访问权限。

### 4.3 本系统侧环境变量配置

| 变量名 | 必选 | 说明 |
|-------|------|------|
| `PROMETHEUS_ENDPOINT` | ✅ | Prometheus 服务地址，如 `http://prometheus.qixuan-soft.internal:9090` |
| `PROMETHEUS_READONLY_TOKEN` | ✅ | 只读查询 Bearer Token |
| `ALERTMANAGER_WEBHOOK_SECRET` | ⬜ | Alertmanager Webhook 签名密钥（HMAC-SHA256）；留空则跳过签名验证 |

### 4.4 集成接口说明

#### 主动查询（Prometheus Range Query）

| 属性 | 值 |
|-----|---|
| 地址 | `GET {PROMETHEUS_ENDPOINT}/api/v1/query_range` |
| 认证 | `Authorization: Bearer {PROMETHEUS_READONLY_TOKEN}` |
| 参数 | `query={promql}&start={unix_ts}&end={unix_ts}&step={step}` |

**四大黄金信号 PromQL 示例**：

```promql
# 5xx 错误率
sum(rate(nginx_ingress_controller_requests_total{status=~"5.."}[5m]))
/ sum(rate(nginx_ingress_controller_requests_total[5m]))

# P99 延迟（毫秒）
histogram_quantile(0.99,
  sum(rate(nginx_ingress_controller_request_duration_seconds_bucket[5m])) by (le)
) * 1000

# CPU 使用率
1 - avg(rate(node_cpu_seconds_total{mode="idle"}[5m]))

# 内存使用率
1 - (node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes)
```

#### 被动接收（Alertmanager Webhook）

| 属性 | 值 |
|-----|---|
| 地址 | `POST https://<your-domain>:8090/webhook/alertmanager` |
| 认证 | 可选 HMAC-SHA256 签名验证 |

**签名验证逻辑**（当 `ALERTMANAGER_WEBHOOK_SECRET` 非空时）：

```python
import hmac, hashlib
expected = hmac.new(secret.encode(), request_body, hashlib.sha256).hexdigest()
provided = request.headers.get("Authorization", "").removeprefix("Bearer ")
if not secrets.compare_digest(expected, provided):
    return 401
```

### 4.5 安全机制

| 机制 | 实现方式 |
|-----|---------|
| 只读访问 | `PROMETHEUS_READONLY_TOKEN` 仅授予查询权限，无写权限 |
| Webhook 签名 | 可选 HMAC-SHA256 签名验证，防止伪造告警 |
| 内网隔离 | Prometheus 仅暴露于内网，不对公网开放 |

### 4.6 常见故障与排查步骤

| 故障现象 | 可能原因 | 排查步骤 |
|---------|---------|---------|
| PromQL 查询返回 401 | Token 无效或过期 | 检查 `PROMETHEUS_READONLY_TOKEN` 是否正确；直接 curl 测试 |
| Alertmanager 未触发 Webhook | route/receiver 配置错误 | 检查 `alertmanager.yml` 中 route 匹配规则；执行 `amtool config check` |
| Webhook 接收到告警但签名验证失败 | 密钥不匹配 | 核对 `ALERTMANAGER_WEBHOOK_SECRET` 与 Alertmanager 侧配置 |
| PromQL 返回空数据 | 时间范围无数据 / 指标名错误 | 在 Prometheus UI 手动验证 PromQL；检查时间窗口参数 |

## 5. 集成四：Elasticsearch（ELK）

### 5.1 集成概述与目的

Qixuan Agent 通过 Elasticsearch REST API 检索应用日志，支持按时间窗口、日志级别、服务名称、异常类型及 Trace ID 进行多维度搜索，辅助运维排障。检索结果在返回前自动脱敏，避免敏感信息泄露。

### 5.2 外部系统侧配置步骤

1. 在 Kibana 或 Elasticsearch API 中创建只读 API Key：

   ```bash
   POST /_security/api_key
   {
     "name": "qixuan-agent-readonly",
     "role_descriptors": {
       "log_reader": {
         "cluster": ["monitor"],
         "indices": [{
           "names": ["*-app-logs*"],
           "privileges": ["read", "view_index_metadata"]
         }]
       }
     }
   }
   ```

   记录响应中的 `encoded` 值，即 `ELK_READONLY_API_KEY`。

2. 确认日志索引命名符合约定 `*-app-logs*`，或按实际生产环境调整（见 5.4 节说明）。

### 5.3 本系统侧环境变量配置

| 变量名 | 必选 | 说明 |
|-------|------|------|
| `ELK_ENDPOINT` | ✅ | Elasticsearch 地址，如 `http://elasticsearch.qixuan-soft.internal:9200` |
| `ELK_READONLY_API_KEY` | ✅ | Elasticsearch API Key（只读），创建方式见 5.2 节 |

### 5.4 集成接口说明

#### 日志检索接口

| 属性 | 值 |
|-----|---|
| 地址 | `POST {ELK_ENDPOINT}/*-app-logs*/_search` |
| 认证 | `Authorization: ApiKey {ELK_READONLY_API_KEY}` |
| Content-Type | `application/json` |

**请求体示例**（时间窗口 + 多字段全文检索）：

```json
{
  "query": {
    "bool": {
      "filter": [
        {"range": {"@timestamp": {"gte": "2025-07-14T00:00:00Z", "lte": "2025-07-14T23:59:59Z"}}},
        {"term": {"level": "ERROR"}}
      ],
      "must": [{
        "multi_match": {
          "query": "NullPointerException",
          "fields": ["message", "exception.stacktrace", "log.message"]
        }
      }]
    }
  },
  "_source": ["@timestamp", "level", "service.name", "message", "exception.class", "trace.id"],
  "size": 100,
  "sort": [{"@timestamp": {"order": "desc"}}]
}
```

**检索字段说明**：

| 字段 | 说明 |
|-----|------|
| `@timestamp` | 日志时间戳 |
| `level` | 日志级别（INFO/WARN/ERROR） |
| `service.name` | 服务名称 |
| `message` | 日志消息 |
| `exception.class` | 异常类名 |
| `trace.id` | 分布式追踪 ID |

> **索引命名约定**：当前使用通配符 `*-app-logs*`，生产环境需按实际索引模式（如 `prod-app-logs-2025.07.14`）调整，避免跨环境检索。

### 5.5 安全机制

| 机制 | 实现方式 |
|-----|---------|
| 最小权限 | API Key 仅授予 `*-app-logs*` 索引的 read 权限 |
| 传输加密 | 生产环境建议启用 Elasticsearch HTTPS（TLS） |
| 自动脱敏 | 返回结果中正则替换以下字段值为 `***REDACTED***`：`password`、`token`、`secret`、`api_key`、`authorization` |
| 内网隔离 | Elasticsearch 不对公网开放 |

**脱敏正则示例**：

```python
import re
SENSITIVE_PATTERN = re.compile(
    r'("(?:password|token|secret|api_key|authorization)"\s*:\s*)"[^"]*"',
    re.IGNORECASE
)
sanitized = SENSITIVE_PATTERN.sub(r'\1"***REDACTED***"', raw_json)
```

### 5.6 常见故障与排查步骤

| 故障现象 | 可能原因 | 排查步骤 |
|---------|---------|---------|
| 请求返回 401 | API Key 无效或过期 | 重新生成 API Key；用 `curl -H "Authorization: ApiKey ..."` 直接测试 |
| 返回 403 | 权限不足 | 确认 API Key 授权索引模式包含目标索引 |
| 查询结果为空 | 索引不存在 / 时间范围无数据 | 在 Kibana Dev Tools 验证索引存在；缩小或扩展时间窗口 |
| 脱敏字段未替换 | 字段名大小写不匹配 | 检查正则标志是否包含 `re.IGNORECASE` |

## 6. 集成五：Kubernetes（K8s）

### 6.1 集成概述与目的

Qixuan Agent 通过宿主机 `kubectl` 命令读取集群资源状态，支持查询 Pod、Deployment、Service、Node、Event、ConfigMap 信息，并自动识别异常 Pod 状态（CrashLoopBackOff、OOMKilled、Error）。写操作（如 Pod 重启）通过 HITL 审批通道执行，不在自动化流程中直接触发。

### 6.2 外部系统侧配置步骤

1. 在 K8s 集群中创建 ClusterRole（只读）：

   ```yaml
   apiVersion: rbac.authorization.k8s.io/v1
   kind: ClusterRole
   metadata:
     name: qixuan-agent-readonly
   rules:
     - apiGroups: [""]
       resources: ["pods", "services", "nodes", "configmaps", "events"]
       verbs: ["get", "list"]
     - apiGroups: ["apps"]
       resources: ["deployments"]
       verbs: ["get", "list"]
   ```

2. 创建 ServiceAccount 并绑定 ClusterRole：

   ```yaml
   apiVersion: v1
   kind: ServiceAccount
   metadata:
     name: qixuan-agent
     namespace: qixuan-system
   ---
   apiVersion: rbac.authorization.k8s.io/v1
   kind: ClusterRoleBinding
   metadata:
     name: qixuan-agent-readonly-binding
   subjects:
     - kind: ServiceAccount
       name: qixuan-agent
       namespace: qixuan-system
   roleRef:
     kind: ClusterRole
     name: qixuan-agent-readonly
     apiGroup: rbac.authorization.k8s.io
   ```

   ```bash
   kubectl apply -f qixuan-agent-rbac.yaml
   ```

3. 获取 ServiceAccount 的 kubeconfig 或 Token，配置宿主机 `~/.kube/config` 确保 `kubectl` 命令可用。

4. 验证权限：

   ```bash
   kubectl auth can-i list pods --as=system:serviceaccount:qixuan-system:qixuan-agent
   # 预期输出：yes
   ```

### 6.3 本系统侧环境变量配置

K8s 集成通过宿主机 `kubectl` 命令执行，无独立环境变量。需确保：

| 条件 | 检查方式 |
|-----|---------|
| `kubectl` 已安装于宿主机 | `kubectl version --client` |
| `~/.kube/config` 配置正确 | `kubectl cluster-info` |
| 当前上下文指向目标集群 | `kubectl config current-context` |

### 6.4 集成接口说明

**工具调用方式**：通过 `subprocess` 执行 `kubectl` 命令，输出格式为 JSON（`-o json`），超时 15 秒。

**允许查询的资源类型**：

| 资源类型 | 示例命令 |
|---------|---------|
| pods | `kubectl get pods -A -o json` |
| deployments | `kubectl get deployments -n <ns> -o json` |
| services | `kubectl get services -n <ns> -o json` |
| events | `kubectl get events -n <ns> --sort-by=.lastTimestamp -o json` |
| nodes | `kubectl get nodes -o json` |
| configmaps | `kubectl get configmap <name> -n <ns> -o json` |

**异常检测逻辑**（自动汇总至 `anomalies` 字段）：

```python
ABNORMAL_STATES = {"CrashLoopBackOff", "OOMKilled", "Error", "ImagePullBackOff"}
anomalies = [
    pod for pod in pods
    if pod["status"]["phase"] not in {"Running", "Succeeded"}
    or any(
        c.get("state", {}).get("waiting", {}).get("reason") in ABNORMAL_STATES
        for c in pod["status"].get("containerStatuses", [])
    )
]
```

**写操作（Pod 重启）**：由 `k8s_pod_restart` 工具触发飞书 HITL 审批卡片，审批通过后方可执行 `kubectl rollout restart`，不在 `ops_tools.py` 中直接实现。

### 6.5 安全机制

| 机制 | 实现方式 |
|-----|---------|
| 最小权限 RBAC | ClusterRole 仅包含 get/list，无 create/update/delete |
| 写操作隔离 | 重启等写操作强制经过 HITL 审批，自动化流程无写权限 |
| 命令超时 | subprocess 超时 15 秒，防止命令挂起 |
| 资源类型白名单 | 仅允许查询六类资源，拒绝超出范围的查询请求 |

### 6.6 常见故障与排查步骤

| 故障现象 | 可能原因 | 排查步骤 |
|---------|---------|---------|
| `kubectl` 命令超时 | 集群 APIServer 不可达 | 检查网络连通性；`kubectl cluster-info` |
| 返回 `Forbidden` | RBAC 权限不足 | 确认 ClusterRoleBinding 已正确创建；`kubectl auth can-i list pods` |
| Pod 异常检测结果为空 | 检测逻辑未覆盖该异常状态 | 检查 Pod 实际状态字段，更新 `ABNORMAL_STATES` 集合 |
| kubeconfig 凭证过期 | ServiceAccount Token 过期 | 重新生成 kubeconfig；使用长期凭证或自动刷新机制 |

## 7. 集成六：内网 vLLM 推理节点（涉密模式）

### 7.1 集成概述与目的

当 Agent 运行在 Profile 名称以 `confidential` 开头的配置下时，所有推理请求自动路由至内网私有化部署的 vLLM 节点（Google Gemma-4-26B），切断所有云端 API 调用（包括 Hugging Face Inference API），确保敏感数据不出内网。

### 7.2 外部系统侧配置步骤

1. 确认宿主机满足 GPU 要求：

   | 配置 | 最低要求 |
   |-----|---------|
   | GPU 型号 | NVIDIA RTX 4090（24GB）或 L20 / A100 |
   | 驱动版本 | ≥ 525.x |
   | NVIDIA Container Toolkit | 已安装（`nvidia-ctk --version`） |

2. 下载模型权重（需 Hugging Face Token）：

   ```bash
   huggingface-cli login --token <HF_TOKEN>
   huggingface-cli download google/gemma-4-26b-a4b-it
   ```

3. 启动 vLLM 服务（通过 Docker Compose）：

   ```bash
   docker compose --profile confidential up -d
   ```

   Docker Compose 中 vLLM 服务关键启动参数：

   ```
   --model google/gemma-4-26b-a4b-it
   --served-model-name google/gemma-4-26b-a4b-it
   --max-model-len 16384
   --gpu-memory-utilization 0.90
   ```

4. 验证服务就绪：

   ```bash
   curl http://qixuan-local-vllm:8000/v1/models \
     -H "Authorization: Bearer qx-local-vllm-secret-key-2026"
   # 预期返回模型列表 JSON
   ```

### 7.3 本系统侧环境变量配置

| 变量名 | 必选 | 说明 |
|-------|------|------|
| `LOCAL_VLLM_HOST` | ✅ | vLLM 服务地址，如 `http://qixuan-local-vllm:8000/v1` |
| `LOCAL_VLLM_API_KEY` | ✅ | vLLM 访问密钥 |
| `LOCAL_VLLM_MODEL` | ✅ | 模型标识符，如 `google/gemma-4-26b-a4b-it` |

### 7.4 集成接口说明

vLLM 服务暴露 OpenAI 兼容接口：

| 属性 | 值 |
|-----|---|
| 地址 | `POST {LOCAL_VLLM_HOST}/chat/completions` |
| 认证 | `Authorization: Bearer {LOCAL_VLLM_API_KEY}` |
| Content-Type | `application/json` |

**路由切换逻辑**：

```python
if profile_name.startswith("confidential"):
    # 切换至本地 vLLM 节点
    client = OpenAI(base_url=LOCAL_VLLM_HOST, api_key=LOCAL_VLLM_API_KEY)
    model = LOCAL_VLLM_MODEL
    # 阻断所有云端 HF API 调用
    disable_cloud_apis()
else:
    # 使用默认云端模型
    client = default_cloud_client
```

### 7.5 安全机制

| 机制 | 实现方式 |
|-----|---------|
| 完全内网隔离 | vLLM 节点不暴露公网端口；涉密模式下云端 API 调用被程序级阻断 |
| 访问认证 | Bearer Token（`LOCAL_VLLM_API_KEY`）保护 vLLM 接口 |
| 模型隔离 | 涉密 Profile 专用模型节点，与普通业务节点物理隔离 |
| 数据不落盘 | vLLM 推理过程不持久化对话内容（需在 vLLM 配置中确认） |

### 7.6 常见故障与排查步骤

| 故障现象 | 可能原因 | 排查步骤 |
|---------|---------|---------|
| vLLM 服务启动后 OOM | GPU 显存不足 | 降低 `--gpu-memory-utilization`（如 0.85）；确认 GPU 显存 ≥ 24GB |
| 模型下载失败 | HF Token 无效或网络不通 | 检查 `huggingface-cli whoami`；配置内网 HF 镜像 |
| 推理请求返回 503 | 服务未就绪 | 查看容器日志 `docker logs qixuan-vllm`；等待模型加载完成 |
| 涉密模式未生效 | Profile 名称未以 `confidential` 开头 | 检查启动时传入的 Profile 名称；确认路由切换逻辑触发 |

## 8. 集成七：本地 Embedding 节点

### 8.1 集成概述与目的

Qixuan Agent 使用本地部署的 BAAI/bge-m3 模型为企业知识库文档生成向量，支持中英双语语义检索（RAG）。与远程 Embedding 服务相比，本地节点避免了敏感文档外传，并降低检索延迟。

### 8.2 外部系统侧配置步骤

通过 Docker Compose 启动 Embedding 服务：

```bash
docker compose up -d qixuan-local-embedding
```

Docker Compose 服务配置参考：

```yaml
services:
  qixuan-local-embedding:
    image: ghcr.io/huggingface/text-embeddings-inference:cpu-1.5
    command: --model-id BAAI/bge-m3 --port 8080
    ports:
      - "8080:8080"
    volumes:
      - ./models:/data
```

验证服务就绪：

```bash
curl http://qixuan-local-embedding:8080/v1/models
# 预期返回 BAAI/bge-m3 模型信息
```

### 8.3 本系统侧环境变量配置

| 变量名 | 必选 | 说明 |
|-------|------|------|
| `LOCAL_EMBEDDING_KEY` | ⬜ | Embedding 服务访问密钥（服务默认无认证时可留空） |

Embedding 服务地址固定为 `http://qixuan-local-embedding:8080`（内部 Docker 网络）。

### 8.4 集成接口说明

服务暴露 OpenAI 兼容 Embeddings 接口：

| 属性 | 值 |
|-----|---|
| 地址 | `POST http://qixuan-local-embedding:8080/v1/embeddings` |
| 认证 | 可选，`Authorization: Bearer {LOCAL_EMBEDDING_KEY}` |
| Content-Type | `application/json` |

**请求体示例**：

```json
{
  "model": "BAAI/bge-m3",
  "input": ["企业知识库文档内容", "Another document in English"]
}
```

**响应体示例**：

```json
{
  "object": "list",
  "data": [
    {"object": "embedding", "index": 0, "embedding": [0.023, -0.145, ...]},
    {"object": "embedding", "index": 1, "embedding": [0.067, -0.032, ...]}
  ],
  "model": "BAAI/bge-m3",
  "usage": {"prompt_tokens": 12, "total_tokens": 12}
}
```

### 8.5 安全机制

| 机制 | 实现方式 |
|-----|---------|
| 内网隔离 | Embedding 节点仅在 Docker 内部网络暴露，不绑定公网 IP |
| 可选认证 | 生产环境建议配置 `LOCAL_EMBEDDING_KEY` |
| 数据不外传 | 知识库内容仅在内网处理，不经过云端接口 |

### 8.6 常见故障与排查步骤

| 故障现象 | 可能原因 | 排查步骤 |
|---------|---------|---------|
| 服务启动慢 | CPU 模式加载大模型耗时 | 属正常现象，等待 2-5 分钟；`docker logs qixuan-local-embedding` 确认加载进度 |
| 请求返回 422 | 输入格式错误 | 确认 `input` 字段为字符串数组而非单字符串 |
| 向量维度异常 | 模型版本不匹配 | 确认镜像 tag 为 `cpu-1.5`；bge-m3 输出维度应为 1024 |

## 9. 集成八：内部 Git 技能仓库

### 9.1 集成概述与目的

Qixuan Agent 的技能（Skill）以 Python 文件形式存储于内部 GitLab 技能仓库。Agent 每 30 分钟自动同步最新技能，实现热加载无需重启。运营人员通过 `/learn` 命令触发新技能草稿自动推送 PR，经人工审核合并后即可上线。

### 9.2 外部系统侧配置步骤

**初始化技能仓库**：

```bash
# 在 GitLab 上创建仓库：ai-platform/qixuan-agent-skills

cd skills/qixuan
git init && git branch -M main
git add .
git commit -m "feat: 初始化首批四大核心技能"
git remote add origin https://git.qixuan-soft.internal/ai-platform/qixuan-agent-skills.git
git push -u origin main
```

**配置 GitLab CI 保护**（推荐）：

- 保护 `main` 分支，禁止直接 push，所有变更须经 MR + 审批

### 9.3 本系统侧配置

在 `config.yaml` 中配置技能仓库：

```yaml
skills:
  git_sync:
    enabled: true
    repo_url: https://git.qixuan-soft.internal/ai/qixuan-agent-skills.git

    sync_interval_minutes: 30
```

在 `.env` 中配置 Token：

| 变量名 | 必选 | 说明 |
|-------|------|------|
| `GIT_SKILL_TOKEN` | ✅ | 技能仓库访问 Token，需 `read_repository`（同步）+ `write_repository`（提交草稿 PR） |

### 9.4 集成接口说明

**自动同步（每 30 分钟）**：

```bash
# 内部调度器执行

git pull origin main
# 热加载：重新扫描并注册新增/变更的技能文件，无需重启服务
```

**`/learn` 命令触发新技能推送**：

```bash
python scripts/learn.py --push-to-git

# 1. 将新技能草稿写入本地文件
# 2. 创建 feature/skill-draft-<timestamp> 分支
# 3. 提交并推送至远端
# 4. 通过 GitLab API 创建 Merge Request（目标 main 分支）
```

### 9.5 安全机制

| 机制 | 实现方式 |
|-----|---------|
| 分支保护 | main 分支禁止直接 push，所有技能须经 MR 审核 |
| Token 最小权限 | 只读同步使用 read 权限；仅 learn 场景使用 write 权限 |
| 技能审查 | CI Pipeline 自动执行语法检查；人工审核确认技能逻辑安全 |

### 9.6 常见故障与排查步骤

| 故障现象 | 可能原因 | 排查步骤 |
|---------|---------|---------|
| 自动同步失败（认证错误） | `GIT_SKILL_TOKEN` 过期 | 在 GitLab 重新生成 Token 并更新 `.env` |
| 热加载后技能未生效 | 文件未被扫描到 | 检查技能文件命名是否符合约定；查看热加载日志 |

## 11. 网络与防火墙配置要求

### 11.1 端口总览

| 端口 | 协议 | 服务 | 方向 | 说明 |
|-----|------|------|------|------|
| 8090 | TCP/HTTPS | Qixuan Agent Gateway | 入站 | 接收飞书事件、GitLab Webhook、Alertmanager Webhook |
| 443 | TCP/HTTPS | 飞书开放平台 API | 出站 | 推送消息、获取用户信息 |
| 443 | TCP/HTTPS | GitLab 内网实例 | 出站 | REST API 调用（MR 信息、评论发布） |
| 9090 | TCP/HTTP | Prometheus | 出站（内网） | PromQL 查询 |
| 9093 | TCP/HTTP | Alertmanager | 出站（内网，可选） | 告警管理接口 |
| 9200 | TCP/HTTP | Elasticsearch | 出站（内网） | 日志检索 |
| 8000 | TCP/HTTP | vLLM 推理节点 | 出站（内网） | 涉密模式推理请求 |
| 8080 | TCP/HTTP | Embedding 节点 | 出站（内网） | 向量化请求 |
| 443 | TCP/HTTPS | 内部 GitLab（技能仓库） | 出站（内网） | Git pull/push |

### 11.2 入站规则

| 来源 | 目标端口 | 协议 | 说明 |
|-----|---------|------|------|
| 飞书开放平台（IP 范围见飞书文档） | 8090 | HTTPS | 事件推送、卡片回调 |
| GitLab 内部实例 | 8090 | HTTPS | Webhook 推送 |
| Alertmanager 内部实例 | 8090 | HTTPS | 告警 Webhook |
| 运维管理网段 | 8090 | HTTPS | 健康检查、调试 |

> **注意**：8090 端口须对飞书开放平台 IP 开放，同时对 GitLab 和 Alertmanager 内网 IP 开放。建议通过 IP 白名单而非完全开放来控制入站访问。

### 11.3 出站规则

| 目标 | 端口 | 说明 | 网络区域 |
|-----|------|------|---------|
| `open.feishu.cn` | 443 | 飞书 API | 公网 |
| `git.qixuan-soft.internal` | 443 | GitLab REST API + Git | 内网 |
| `prometheus.qixuan-soft.internal` | 9090 | Prometheus 查询 | 内网 |
| `elasticsearch.qixuan-soft.internal` | 9200 | ELK 日志检索 | 内网 |
| `qixuan-local-vllm` | 8000 | 私有推理节点 | Docker 内网 |
| `qixuan-local-embedding` | 8080 | Embedding 节点 | Docker 内网 |

### 11.4 涉密模式网络要求

在 `confidential` Profile 激活时，需在防火墙层面**阻断**以下出站流量：

| 目标域名 | 端口 | 说明 |
|---------|------|------|
| `api.huggingface.co` | 443 | Hugging Face Inference API |
| `*.openai.com` | 443 | OpenAI API（若有配置） |
| 其他云端 LLM 服务 | 443 | 按实际使用情况补充 |

> 防火墙拦截作为程序级阻断的兜底层，确保即使代码逻辑出现漏洞，数据也不会外传。

### 11.5 TLS 证书要求

- Qixuan Agent Gateway（端口 8090）**必须**配置有效 TLS 证书（CA 签发或企业内部 CA）
- 飞书开放平台要求回调 URL 为 HTTPS，自签名证书**不被接受**
- 内网服务（Prometheus、Elasticsearch、GitLab）建议启用 HTTPS，可使用企业内部 CA 签发证书
