## 2. 系统概述与建设目标

### 2.1 项目背景

启煊软件（Qixuan Software）面向企业客户提供软件研发与数字化转型服务。随着业务规模扩大，需求分析、代码审查、运维巡检、版本发布等高频研发管理工作对人力资源的消耗持续上升，同时对响应时效、知识积累与流程合规性提出了更高要求。

Qixuan Agent 在 Hermes Agent Architecture 技术底座之上，融合 Hugging Face 云端推理与本地私有化推理节点，构建一套具备持久记忆、技能自进化、多端协同能力的企业级 AI 智能体中枢。

### 2.2 建设目标

| 目标维度 | 具体描述 |
|----------|----------|
| **持久记忆** | 以 SQLite FTS5 全文检索记忆库为核心，跨会话保留项目决策、缺陷处理经验、客户关键信息，支持中文全文检索与前缀通配查询 |
| **技能自进化** | 通过 `/learn` 指令从历史会话轨迹中自动生成标准 SKILL.md 草稿，并可推送至内部 Git 仓库，实现知识的持续沉淀与技能库扩充 |
| **多端协同** | 统一接入飞书、钉钉、企业微信机器人，GitLab Webhook，Alertmanager 告警，以及 Cron 定时调度，提供一致的智能体交互体验 |
| **安全合规** | 通过多租户 Profile 隔离、HITL 人工审批、最小权限原则和审计日志，满足企业级数据安全与操作合规要求 |
| **涉密数据不出网** | 对标记为涉密的 Profile，强制路由至内网 vLLM 节点，确保敏感数据全程在内网闭环处理 |

### 2.3 系统定位

Qixuan Agent 定位为企业研发管理的 AI 中枢，不替代现有研发工具链，而是作为智能协作层，与 GitLab、Prometheus、ELK、飞书等系统深度集成，以工具调用的方式完成跨系统的信息聚合与自动化操作。

## 4. 五层架构详述

### 4.1 第一层：多端接入网关层（Gateway Layer）

#### 4.1.1 层职责

网关层是系统的统一入口，负责接收来自多种外部渠道的请求，完成协议适配、事件解析与请求规范化，将其转换为内部统一格式后路由至治理层。

#### 4.1.2 核心模块

**统一 Webhook 路由入口（`gateway/webhook_router.py`）**

基于 FastAPI 构建，监听 8090 端口，提供以下路由端点：

| 端点路径 | 来源 | 触发技能 |
|----------|------|----------|
| `POST /webhook/feishu` | 飞书机器人 @事件 | 意图识别后动态分派 |
| `POST /webhook/gitlab` | GitLab MR/Tag Webhook | qixuan-code-reviewer / qixuan-release-notes |
| `POST /webhook/alertmanager` | Alertmanager 告警 | qixuan-ops-sentinel |
| `POST /webhook/dingtalk` | 钉钉机器人 @事件 | 意图识别后动态分派 |
| `POST /webhook/wecom` | 企业微信机器人 @事件 | 意图识别后动态分派 |

**飞书网关适配器（`gateway/feishu/feishu_gateway.py`）**

负责飞书消息签名验证、消息体解析（文本/卡片/文件），将飞书消息格式转换为内部标准请求结构，并处理飞书的 `challenge` 验证握手请求。

**定时调度器（`scripts/cron_runner.py`）**

以独立进程运行，管理所有定时触发任务：

- 工作日 08:00 触发 `qixuan-ops-sentinel` 执行晨间运维巡检
- 每 30 分钟同步 `skills/qixuan/` 目录至内部 Git 仓库

#### 4.1.3 关键设计决策

- **协议隔离**：每种 IM 渠道的签名验证与报文解析逻辑封装在各自的 Gateway 适配器中，`webhook_router.py` 仅感知统一的内部请求结构，不直接处理各平台细节。
- **幂等性保护**：所有 Webhook 请求通过 `event_id` 去重，防止网络重试导致技能重复执行。
- **超时防护**：FastAPI 请求处理超时设置为 30 秒，避免慢速下游阻塞网关进程。

### 4.2 第二层：企业治理与隔离层（Enterprise Governance Layer）

#### 4.2.1 层职责

治理层是系统安全与合规的核心屏障，负责多租户数据隔离、高危操作拦截审批、模型路由决策和完整操作审计。所有请求必须经过治理层处理后，才可进入 Agent 核心层。

#### 4.2.2 核心模块

**多租户 Profile 隔离**

每个客户或项目映射为一个独立的 Profile，拥有独立的运行时数据目录和数据库文件：

```
data/profiles/<profile_id>/
    ├── USER.md        # 该 Profile 的角色偏好与人格设定
    └── MEMORY.md      # 该 Profile 的项目规约与长期记忆

data/sqlite/<profile_id>/qixuan_memory.db   # 独立 SQLite 数据库
```

Profile ID 命名规则：前缀包含 `confidential_` 时，自动触发涉密路由，强制将所有 LLM 调用路由至内网 vLLM 节点。

**安全模型路由器（`governance/router.py`）**

实现三级路由优先级决策链：

```
优先级 1（最高）：Profile ID 包含 confidential_ 前缀
                  → 强制路由至 confidential_local（内网 vLLM）
                  → 任何情况下不可覆盖

优先级 2：请求显式指定 role 参数
                  → 路由至对应角色模型

优先级 3：当前激活技能在路由覆盖表中有配置
                  → 路由至技能指定的模型角色

优先级 4（默认）：路由至 primary（GLM-5.1）
```

技能路由覆盖配置表：

| 技能名称 | 目标模型角色 | 原因 |
|----------|-------------|------|
| qixuan-req-analyzer | coding | 需求分析需要长上下文与代码理解能力 |
| qixuan-code-reviewer | coding | 代码审查需要高精度代码推理能力 |
| qixuan-ops-sentinel | primary | 运维巡检需要复杂推理与任务规划能力 |
| qixuan-release-notes | coding | 发布说明生成需要代码变更理解能力 |

**HITL 人工审批（`governance/hitl.py`）**

对以下高危工具集合的调用，系统在执行前强制进入人工审批流程：

```python
HIGH_RISK_TOOLS = {
    "git_push",
    "db_execute_write",
    "send_external_email",
    "deploy_staging",
    "k8s_pod_restart"
}
```

审批流程：
1. 工具调用被拦截，状态置为 `pending`，记录至 `audit_log` 表
2. 向飞书发送结构化审批卡片，包含工具名称、调用参数摘要、关联会话上下文
3. 轮询等待审批人操作，轮询间隔 5 秒
4. 审批通过 → 状态更新为 `approved`，继续执行工具，完成后置为 `executed`
5. 审批拒绝 → 抛出 `HITLRejectedError`，状态置为 `rejected`
6. 超时 600 秒未操作 → 抛出 `HITLTimeoutError`，状态置为 `timeout`

**审计日志**

所有工具调用（含普通工具和经 HITL 审批的高危工具）均写入 SQLite `audit_log` 表，记录内容包括：调用工具名称、输入参数哈希值（原始参数不落库）、审批人、创建时间、执行时间及最终状态。

#### 4.2.3 关键设计决策

- **涉密不可覆盖原则**：涉密路由在代码层面作为最高优先级硬编码，无法通过任何运行时参数绕过，确保敏感数据的绝对内网闭环。
- **参数哈希而非明文**：审计日志仅存储输入参数的哈希值，避免敏感业务数据以明文形式持久化在日志中。
- **超时保护**：HITL 超时机制防止因审批人未响应而导致任务长期阻塞，600 秒后系统自动取消并通知相关方。

### 4.3 第三层：认知与进化核心层（Agent Core）

#### 4.3.1 层职责

Agent 核心层是系统的"大脑"，负责维护对话上下文、调用工具完成任务、管理持久记忆，以及从历史经验中生成新技能。

#### 4.3.2 核心模块

**双层精简上下文**

为控制每次 LLM 调用的 Token 消耗，系统对注入 LLM 系统提示的上下文设置严格的 Token 预算：

| 上下文文件 | 内容定位 | Token 上限 |
|------------|----------|-----------|
| `USER.md` | 当前 Profile 的角色设定、偏好配置、工作方式说明 | ≤ 1,500 Tokens |
| `MEMORY.md` | 项目核心规约、架构决策、关键约定 | ≤ 2,500 Tokens |
| **合计** | 静态上下文总预算 | **≤ 4,000 Tokens** |

**SQLite FTS5 全文检索记忆库（`tools/memory/memory_tools.py`）**

记忆库提供跨会话的持久化知识存储，支持高效的中文全文检索：

- **FTS5 引擎配置**：`tokenize = 'unicode61 remove_diacritics 2'`，支持 Unicode 标准分词，兼容中英文混合内容
- **中文检索双策略**：优先使用 FTS5 前缀通配查询（`keyword*`），当结果为空时自动降级至 `LIKE '%keyword%'` 回退策略
- **四类记忆分类**：

| 分类标识 | 含义 | 典型写入场景 |
|----------|------|-------------|
| `skill_experience` | 技能执行经验 | 技能执行成功或失败后的总结 |
| `project_decision` | 项目决策记录 | 架构选型、技术决策 |
| `bug_resolution` | 缺陷处理记录 | 线上问题的根因与解决方案 |
| `customer_note` | 客户关键信息 | 客户需求偏好、特殊约定 |

**技能自进化（`scripts/learn.py`）**

`/learn` 指令触发学习流程：
1. 从当前或指定会话的完整对话轨迹（工具调用序列 + 结果）中提取执行模式
2. 通过 LLM 推断技能的触发条件、工具组合、权限需求
3. 生成符合 SKILL.md 协议规范的技能草稿文件
4. 可选推送至内部 Git 仓库，经人工审核后合并至 `skills/qixuan/` 目录

#### 4.3.3 关键设计决策

- **上下文预算硬性约束**：4,000 Tokens 的静态上下文预算是在推理成本与记忆有效性之间做出的工程权衡，避免长系统提示造成的性能退化，同时通过动态记忆检索补充相关知识。
- **记忆与上下文分离**：`MEMORY.md` 存放高频通用的项目级规约，低频或会话特定的知识通过记忆检索工具在需要时动态召回，两者不重叠。

### 4.4 第四层：安全执行沙盒层（Execution Sandbox）

#### 4.4.1 层职责

执行沙盒层管理所有外部系统的工具调用，以最小权限原则封装各类集成接口，并通过容器隔离限制 Agent 对宿主机资源的访问范围。

#### 4.4.2 核心模块

**Docker 受限代理（`qixuan-sandbox-proxy`）**

基于 `tecnativa/docker-socket-proxy` 实现，将 Docker socket 以受限方式暴露给 Agent 容器：

| Docker API 权限 | 状态 |
|-----------------|------|
| CONTAINERS | ✅ 允许 |
| IMAGES | ✅ 允许 |
| NETWORKS | ✅ 允许 |
| EXEC | ✅ 允许 |
| POST | ✅ 允许 |
| VOLUMES | ❌ 禁止 |
| SYSTEM | ❌ 禁止 |
| SWARM | ❌ 禁止 |

**K8s 只读巡检（`tools/ops/ops_tools.py`）**

Agent 对 Kubernetes 集群的操作严格限定为只读查询，仅允许以下资源类型的 `get` 操作：

```
pods / deployments / services / events / nodes / configmaps
```

写操作（如 `k8s_pod_restart`）归入高危工具集合，必须经过 HITL 审批。

**Prometheus 只读查询（`tools/ops/ops_tools.py`）**

仅开放 Prometheus HTTP API 中的查询接口（`/api/v1/query`、`/api/v1/query_range`），不开放任何管理接口。

**ELK 日志检索（`tools/ops/ops_tools.py`）**

通过 Elasticsearch Query DSL 检索日志，自动对以下字段执行脱敏处理后再返回结果：密码字段、Token 字段、手机号、身份证号、银行卡号等敏感信息模式。

**GitLab 只读令牌（`tools/git/git_tools.py`）**

GitLab Personal Access Token 仅申请以下最小权限范围：

| 权限 | 用途 |
|------|------|
| `read_repository` | 读取代码、获取 diff |
| `comment_mr` | 在 MR 上发布代码审查评论 |

不申请 `write_repository`、`api`、`sudo` 等高权限。

#### 4.4.3 关键设计决策

- **沙盒代理优先于 socket 直挂**：通过 `docker-socket-proxy` 而非直接挂载 `/var/run/docker.sock`，从根本上消除 Agent 容器逃逸并以 root 权限操作宿主机的风险。
- **禁用 VOLUMES 权限**：防止 Agent 在未经授权的情况下挂载宿主机目录，保护宿主机文件系统。

---

### 4.5 第五层：混合模型路由层（Model & Resource Layer）

#### 4.5.1 层职责

模型路由层管理所有 LLM 调用，根据治理层的路由决策，将推理请求分发至云端 HF Router 或内网推理节点，并管理 Embedding 计算资源。

#### 4.5.2 模型角色配置

| 角色标识 | 模型 | 推理后端 | Temperature | Max Tokens | 适用场景 |
|----------|------|----------|-------------|------------|----------|
| `primary` | zai-org/GLM-5.1 | HF Router | 0.2 | 16,384 | 复杂任务规划、多步推理 |
| `coding` | Qwen/Qwen3-235B-A22B | HF Router | 0.1 | 32,768 | 代码审查、需求分析、代码生成 |
| `fast` | deepseek-ai/DeepSeek-V4-Flash | HF Router（cheapest） | 0.1 | 4,096 | 意图分类、文本摘要、快速响应 |
| `confidential_local` | google/gemma-4-26b-a4b-it | 内网 vLLM（:8000） | — | — | 涉密 Profile，数据零出网 |
| `embedding` | BAAI/bge-m3 | 内网 TEI（:8080） | — | — | 记忆检索向量化、语义相似度计算 |

#### 4.5.3 内网推理节点

| 服务名称 | 镜像 | 端点 | 用途 |
|----------|------|------|------|
| `qixuan-local-vllm` | `vllm/vllm-openai:latest` | `http://qixuan-local-vllm:8000/v1` | 涉密数据 LLM 推理，需 GPU |
| `qixuan-local-embedding` | `ghcr.io/huggingface/text-embeddings-inference:cpu-1.5` | `http://qixuan-local-embedding:8080/v1` | 文本向量化，CPU 运行 |

#### 4.5.4 关键设计决策

- **`coding` 角色使用低温度（0.1）**：代码类任务要求输出高确定性，低温度减少随机采样带来的语法错误和逻辑偏差。
- **`fast` 角色选用 cheapest 路由**：意图分类和摘要任务对响应延迟敏感、对精度容忍度较高，cheapest 路由在成本与速度上更优。
- **`embedding` 仅部署 CPU 版本**：BGE-M3 的向量化推理计算量相对较小，CPU 版本 TEI 在正常并发场景下延迟可接受，避免占用 GPU 资源。

## 6. 数据模型设计

### 6.1 SQLite 数据库表结构

每个 Profile 拥有独立的数据库文件：`data/sqlite/<profile_id>/qixuan_memory.db`

#### 6.1.1 `memory_fts`（FTS5 虚拟表）

```sql
CREATE VIRTUAL TABLE memory_fts USING fts5(
    session_id,         -- 会话标识，用于关联同一次对话的记忆
    timestamp,          -- 记忆写入的 ISO 8601 时间戳
    category UNINDEXED, -- 分类标识（skill_experience/project_decision/
                        --           bug_resolution/customer_note）
    tags,               -- 空格分隔的标签列表，参与全文检索
    title,              -- 记忆标题，简短描述
    content,            -- 记忆正文，完整描述
    tokenize = 'unicode61 remove_diacritics 2'
);
```

#### 6.1.2 `memory_meta`（普通表）

```sql
CREATE TABLE memory_meta (
    rowid       INTEGER PRIMARY KEY,  -- 与 memory_fts 的 rowid 一一对应
    profile     TEXT    NOT NULL,     -- Profile ID，冗余存储用于跨库校验
    project_id  TEXT,                 -- 关联项目标识（可为空）
    source      TEXT,                 -- 记忆来源（manual/learn/auto）
    created_at  TEXT    NOT NULL,     -- 创建时间（ISO 8601）
    token_count INTEGER              -- 该条记忆的 Token 数量，用于预算管理
);
```

**关联关系**：`memory_meta.rowid` = `memory_fts.rowid`，通过 rowid 进行一对一关联，不使用外键约束（SQLite FTS5 虚拟表不支持外键）。

#### 6.1.3 `audit_log`（审计日志表）

```sql
CREATE TABLE audit_log (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    profile     TEXT    NOT NULL,     -- 操作所属 Profile ID
    session_id  TEXT    NOT NULL,     -- 关联会话 ID
    tool_name   TEXT    NOT NULL,     -- 被调用的工具名称
    input_hash  TEXT    NOT NULL,     -- 工具输入参数的 SHA-256 哈希
    status      TEXT    NOT NULL      -- 状态枚举：
                                      -- pending / approved / rejected /
                                      -- executed / timeout
                CHECK(status IN ('pending','approved','rejected',
                                 'executed','timeout')),
    approver    TEXT,                 -- 审批人标识（HITL 专用，其余为 NULL）
    created_at  TEXT    NOT NULL,     -- 记录创建时间（ISO 8601）
    executed_at TEXT                  -- 工具实际执行完成时间（ISO 8601）
);

CREATE INDEX idx_audit_profile_session
    ON audit_log(profile, session_id);
CREATE INDEX idx_audit_status
    ON audit_log(status);
```

### 6.2 Profile 目录结构

```
data/
├── profiles/
│   ├── default/
│   │   ├── USER.md           # 默认 Profile 角色设定（≤1500 Tokens）
│   │   └── MEMORY.md         # 默认 Profile 项目规约（≤2500 Tokens）
│   ├── <client_a>/
│   │   ├── USER.md
│   │   └── MEMORY.md
│   └── confidential_<client_b>/  # 涉密 Profile，强制内网路由
│       ├── USER.md
│       └── MEMORY.md
└── sqlite/
    ├── default/
    │   └── qixuan_memory.db
    ├── <client_a>/
    │   └── qixuan_memory.db
    └── confidential_<client_b>/
        └── qixuan_memory.db
```

### 6.3 关键约束说明

| 约束类型 | 约束内容 |
|----------|----------|
| Token 预算 | USER.md ≤ 1,500 Tokens，MEMORY.md ≤ 2,500 Tokens，系统在写入时校验并拒绝超出预算的更新 |
| Profile 隔离 | 每次 LLM 调用和工具调用都携带 `profile_id`，记忆查询强制按 `profile` 字段过滤，禁止跨 Profile 读取 |
| 审计完整性 | `audit_log` 中所有工具调用（包括普通工具）均有记录，不允许绕过审计模块直接调用工具 |
| 参数脱敏 | 写入 `input_hash` 前，原始参数中的密码、Token、密钥等字段先被掩码替换，再计算哈希 |

## 7. 安全架构

Qixuan Agent 的安全体系由三大核心机制构成，分别从数据隔离、操作权限和人工控制三个维度提供系统性保护。

### 7.1 数据隔离机制

#### 7.1.1 多租户 Profile 隔离

每个 Profile 的配置文件、上下文记忆和 SQLite 数据库完全独立存储。Agent 核心在处理每条请求时，严格绑定 `profile_id` 参数，所有数据读写操作均以 `profile_id` 作为强制过滤条件，从应用层确保租户间数据不可互访。

#### 7.1.2 涉密数据不出网

通过 Profile ID 的 `confidential_` 前缀约定与路由器中的最高优先级硬编码，涉密 Profile 的所有 LLM 推理请求强制路由至内网 `qixuan-local-vllm` 节点，网络层面通过 Docker 网络隔离确保该节点无外网出口。任何涉密数据在全流程中不经过 Hugging Face 等外部云端服务。

#### 7.1.3 审计日志完整性

`audit_log` 表记录所有工具调用行为，输入参数以哈希形式存储而非明文，确保可审计性的同时防止敏感参数二次泄露。

### 7.2 最小权限机制

#### 7.2.1 Docker Socket 受限代理

Agent 容器通过 `qixuan-sandbox-proxy` 访问 Docker 能力，代理层在 API 层面屏蔽了 `VOLUMES`、`SYSTEM`、`SWARM` 等高风险权限，即使 Agent 被攻击者控制，也无法通过 Docker API 完成容器逃逸或宿主机破坏。

#### 7.2.2 外部系统只读令牌

| 外部系统 | 权限范围 | 不申请的权限 |
|----------|----------|-------------|
| GitLab | read_repository, comment_mr | write_repository, api, delete |
| Kubernetes | get（指定资源类型） | create, update, delete, patch |
| Prometheus | /api/v1/query, /api/v1/query_range | 管理接口、告警规则写入 |
| Elasticsearch | 只读查询 DSL | 索引管理、文档写入 |

#### 7.2.3 ELK 日志自动脱敏

在返回日志内容前，系统自动对结果中的密码字段、Token 字段、手机号码（`1[3-9]\d{9}`）、身份证号等敏感模式执行正则替换脱敏，防止运维排障过程中意外暴露生产敏感数据。

### 7.3 HITL 人工控制机制

HITL 机制作为系统行为安全的最后一道防线，通过人工审批对高危工具调用进行强制拦截，确保对生产环境的破坏性操作始终有人工确认。

**高危工具边界定义**（需人工审批）：

| 工具 | 操作类型 | 风险级别 |
|------|----------|----------|
| `git_push` | 代码推送至远程仓库 | 高：可能覆盖生产代码 |
| `db_execute_write` | 数据库写操作 | 高：数据不可逆修改 |
| `send_external_email` | 向外部发送邮件 | 中：信息泄露或误发 |
| `deploy_staging` | 预发布环境部署 | 高：影响测试环境稳定性 |
| `k8s_pod_restart` | Pod 重启 | 高：影响线上服务可用性 |

**安全降级策略**：当 HITL 审批超时（600s）或被拒绝时，系统选择最保守的策略——取消操作并通知，不会在无人确认的情况下自动重试高危操作。

## 9. 扩展性设计

### 9.1 新增技能

技能以标准 `SKILL.md` 文件描述，增加一个新技能的操作步骤如下：

**步骤 1**：在 `skills/qixuan/` 目录下创建技能目录，如 `skills/qixuan/qixuan-new-skill/`

**步骤 2**：编写 `SKILL.md` 文件，包含标准 YAML frontmatter：

```yaml
---
name: qixuan-new-skill
version: 1.0.0
description: "技能功能描述"
triggers:
  - type: feishu_mention
    pattern: "/new-skill"
  - type: gitlab_webhook
    event: merge_request
tools:
  - memory_search
  - file_writer
permissions:
  - readonly
---
```

**步骤 3**：如需技能路由覆盖（指定特定模型角色），在 `governance/router.py` 的路由覆盖配置表中添加映射记录。

**步骤 4**：在 `gateway/webhook_router.py` 的意图识别规则中注册触发模式。

**步骤 5**：通过 `scripts/learn.py` 验证技能执行路径，确认工具调用链路正常。

技能变更自动通过每 30 分钟的 Git 同步任务分发至所有运行中的 Agent 实例。

### 9.2 新增 Profile（租户）

**步骤 1**：创建 Profile 目录和初始上下文文件：

```bash
mkdir -p data/profiles/<new_profile_id>
# 编写 USER.md（≤1500 Tokens）和 MEMORY.md（≤2500 Tokens）
```

**步骤 2**：初始化该 Profile 的 SQLite 数据库（由 `scripts/init.sh` 自动执行，或手动触发）：

```bash
mkdir -p data/sqlite/<new_profile_id>
# init.sh 自动创建 memory_fts、memory_meta、audit_log 三张表
```

**步骤 3**：若为涉密 Profile，将 Profile ID 命名为 `confidential_<client_name>`，路由器自动识别并强制内网推理，无需额外配置。

**步骤 4**：在 IM 机器人配置中，将对应客户的会话或群组绑定至新 Profile ID。

Profile 层面完全隔离，新增 Profile 不影响任何现有 Profile 的运行。

### 9.3 新增模型节点

**场景一：在 HF Router 中切换或增加云端模型**

在 `config/config.yaml` 的 `models` 配置块中新增角色定义，指定模型标识符和参数：

```yaml
models:
  new_role:
    provider: hf_router
    model: "org/model-name"
    temperature: 0.1
    max_tokens: 8192
```

**场景二：新增内网推理节点**

在 `docker-compose.yml` 中新增服务定义：

```yaml
services:
  qixuan-new-local-node:
    image: vllm/vllm-openai:latest
    environment:
      - MODEL=/models/new-model
    networks:
      - qixuan-net
    # 不对外暴露端口，仅内网访问
```

在 `config/config.yaml` 的模型配置中添加对应角色，`endpoint` 指向新容器的内部地址：

```yaml
models:
  new_local_role:
    provider: openai_compatible
    endpoint: "http://qixuan-new-local-node:8000/v1"
    model: "new-model"
```

**场景三：为现有技能指定新模型角色**

仅需在 `governance/router.py` 的技能路由覆盖表中修改映射记录，无需改动技能本身或其他代码。
